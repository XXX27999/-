# 第十轮｜竞拍仓库「藏品图被格子遮盖」根因定论与修复（2026-09-22）

> 承接第九轮「参照结算界面仓库改造」。前九轮均在「格子像素 / 层级 / ZOrder / 裁切」方向迭代，**均未命中**。
> 第十轮用「活体探针 + 原始截图通道剖面」重新取证，定位到真正的遮挡源，并给出单点修复。

## 一、最终根因（代码级，单点）

**文件**：`Script/Function/AuctionTestUIService.lua`
**位置**：`RefreshWarehouse` 内藏品覆盖层显示状态设置处（原第 1084 / 1088-1089 行）

```lua
-- 修复前
local buttonColor = resourceApplied and TRANSPARENT_CLICK_LAYER_COLOR or placeholderColor
...
button:SetBackgroundColor(buttonColor)
button:SetVisibility(ESlateVisibility.Visible)
```

**问题链**：

| 环节 | 事实 |
|---|---|
| `placeholderColor` 取值 | `qualityColor or KNOWN_OUTLINE_UNKNOWN_QUALITY_COLOR` |
| `KNOWN_OUTLINE_UNKNOWN_QUALITY_COLOR` | `{R=0.46, G=0.50, B=0.56, A=0.96}` —— **A=0.96 近不透明** |
| `resourceApplied=false` 的触发面 | 藏品**身份未公开 / 纹理未解析**时成立，即竞拍前期**绝大多数格** |
| 该按钮属于谁 | **藏品覆盖层**（`CollectibleButton%02d`），层级高于仓库背景格 |
| 叠加结果 | 在仓库格之上盖一块 **96% 不透明灰板** |

→ 用户看到的「**藏品图片在格子图片下面、被格子图片遮挡**」，
   **遮挡物不是格子，而是覆盖层自己的点击层按钮**。这是一个**归因错位**了九轮的 bug。

**为什么第九轮「像素写 ItemImage」没能解决**：
第九轮改的是**背景格**（`CollectibleCodexItemUI` 内 `ItemButton` / `ItemImage`）这一层，
而覆盖层的 `CollectibleButton` 是**另一个控件、另一条代码路径**，未被触及。

```lua
-- 修复后
```

### 3.3 `AuctionWarehouseCellService.lua`（新增像素访问器）

```lua

    local cellWidget = AuctionWarehouseCellService.GetCell(widget, cellIndex)
    if cellWidget == nil then

    return cellWidget.ItemImage
```

## 七、方法论纠错（写进 §0 铁律候选）

**「谁在遮挡」不能靠属性推断，必须同时做「被遮物属性 + 源图通道剖面」两件事。**

本轮之所以前九轮失准，是因为一直把注意力放在**背景格**这一侧（因为我们「知道」格子是底、覆盖层是上），
而从未去读**覆盖层自己**的属性。第九轮探针已测出覆盖层 `Visibility=3 / SlotZ=40`，
但**没有测它的 `BackgroundColor`** —— 缺口就在这一个字段。

→ **新增排查纪律**：判「无像素」时，对**遮挡候选链上的每一个控件**逐一读
`Visibility` + `BackgroundColor.A`（按钮）/ `ColorAndOpacity.A`（图片/文本）/ `Brush.Color`（Border），
**不要只读被遮物的**。
