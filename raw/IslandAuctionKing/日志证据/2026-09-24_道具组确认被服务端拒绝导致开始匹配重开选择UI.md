# 道具组确认被服务端拒绝导致开始匹配重开选择 UI

## 1. 结论

用户看到的现象不是「开始匹配按钮失效」，也不是「二次匹配被取消」，而是道具组确认从未在服务端成功：

1. 客户端只凭 `AuctionPrivateState.OwnedProps` 中组内 4 件仪器全齐，就把道具组判定为 `ownership=owned`。
2. 客户端 `Confirm` 发出 RPC 后不等待服务端结果，直接隐藏道具选择 UI，并返回 `success=true`。
3. 服务端只认可 `player.PropGroups[groupName] > 0` 或临时测试授权；本局 `inventoryCount=0`、`testGrant=false`，因此返回 `PropGroupUnavailable`。
4. 服务端拒绝后 `PropSelectionConfirmed` 仍为 `false`。
5. 再次点击开始匹配时，`AuctionHubUIService.OnMatchClicked` 读到 `propReady=false`，按设计重新打开道具选择 UI，因此没有进入官方二次匹配。

核心矛盾是**客户端与服务器对「拥有道具组」的判定口径不一致**，不是匹配入口本身故障。

## 3. 两端判定口径差异

### 3.1 客户端按单件拥有态判整组已拥有

代码：`Script\Function\AuctionPropSelectUIService.lua`

- `IsItemOwned`（527-537）：读取 `AuctionPrivateState.OwnedProps`（或 `Props`）判断单件是否拥有。
- `GetGroupOwnership`（542-565）：
  - 先读 `privateState.PropGroups[groupName]`，组库存大于 0 才直接返回 `owned`。
  - 组库存为 0 时，遍历 `group.ItemNames`，用 `OwnedProps` 统计 `ownedCount`。
  - 当 `ownedCount >= #itemNames` 时返回 `ownership="owned"`。
- `Confirm`（1095-1148）：
  - 只要客户端判定 `ownership=="owned"`，就允许发 RPC。
  - `pcall` 成功后立即 `AuctionPropSelectUIService.Hide()`，并返回 `success=true`，不等待服务端业务结果。

本局日志中 `OwnedProps` 有 4 件、`PropGroups` 为空，因此客户端稳定得到 `ownedCount=4 total=4 ownership=owned`。

### 3.2 服务端只认组库存或测试授权

代码：`Script\Function\CharacterPropTestGrantService.lua`

- `ResolvePropGroupAccess`（91-109）：
  - `inventoryCount = player.PropGroups[groupName]`。
  - `testGrant = player.CharacterPropTestGrant.PropGroups[groupName] > 0`。
  - `allowed = inventoryCount > 0 or testGrant`。
- `GrantAll`（7-61）明确跳过道具组测试授权，`groupCount=0`。

代码：`Script\Function\AuctionPlayerService.lua`

- `SelectPropGroup`（456-487）调用 `ResolvePropGroupAccess`；`hasAccess=false` 时直接返回 `PropGroupUnavailable`，不写 `SelectedPropGroup`，也不写 `PropSelectionConfirmed`。
- `BuildPrivateState`（816-845）同时下发 `PropGroups` 与 `OwnedProps`，所以客户端能看到单件拥有态，但服务端并不把单件全齐视为道具组可用。

## 4. 为什么点击开始匹配会重开道具选择 UI

代码：`Script\Function\AuctionHubUIService.lua:592-642`

`OnMatchClicked` 的判断顺序是：

1. `houseReady` 不通过 -> 打开拍卖场。
2. `CharacterSelectionConfirmed ~= true` -> 打开角色选择。
3. `PropSelectionConfirmed ~= true` -> 打开道具选择。
4. 三项都就绪且金币达标 -> 调用 `AuctionRematchService.HandleMatchButtonClicked`。

本局服务端拒绝道具组确认后，`PropSelectionConfirmed` 始终为 `false`。因此每次点击开始匹配都会走到第 3 步，打开道具选择 UI，从未执行第 4 步。

## 5. 修复方向

必须先确定产品口径，不能只改客户端或只改服务端：

### 方案 A：道具组必须整组购买或拥有（与当前服务端口径一致）

1. 客户端 `GetGroupOwnership` 不再仅凭 `OwnedProps` 全齐返回 `owned`，应与服务端一致，只认 `PropGroups[groupName] > 0` 或服务端明确下发的可用权限。
2. `Confirm` 不应在 RPC 发出后立即隐藏 UI；应等待 `ClientAuctionOperationResult`。
3. 收到 `Success=false` 时保留或重新打开道具选择 UI，并向玩家显示失败原因。
4. `PropSelectionConfirmed=true` 只能由服务端确认后下发。

### 方案 B：集齐组内所有单件即可选择该组

1. 服务端 `ResolvePropGroupAccess` 必须增加 `OwnedProps` 全齐判定。
2. 同时明确是否扣除单件、是否仍按组库存扣除，以及 `PropGroups` 与 `OwnedProps` 的权威关系。
3. 该方案会改变玩法与存档语义，不能仅凭当前日志推断，需产品明确确认。

## 6. 建议补充日志

若后续修复该问题，建议补充以下可验证日志：

1. 客户端 `Confirm`：记录 `groupStock`、`ownedCount`、`total`、`requestStarted`，并区分「RPC 已发出」与「服务端业务成功」。
2. 客户端操作结果回调：记录 `Action`、`Success`、`Message`、是否保留道具 UI、是否重新打开。
3. 服务端 `ResolvePropGroupAccess`：记录 `groupName`、`PropGroups[groupName]`、`testGrant`、`OwnedProps` 全齐数量。
4. 服务端 `SelectPropGroup`：记录拒绝后 `PropSelectionConfirmed=false`，以及是否向客户端发送可展示的失败原因。

## 7. 本轮排除

- 不是「开始匹配按钮点击无响应」：日志明确有 `OnMatchClicked` 入口与 `opened=prop` 出口。
- 不是「二次匹配被取消」：客户端从未走到 `AuctionRematchService.HandleMatchButtonClicked`。
- 不是「服务端没有收到道具组 RPC」：DS 明确收到 `SelectPropGroup`，并返回 `PropGroupUnavailable`。
- 不是「客户端 `pcall` 失败」：日志 `requestOK=true` 只代表 RPC 发送动作未抛异常。
- 当前 `Gold=0` 与 `groupStockCount=0` 是同一链路中的相关事实，但本次「点击开始匹配重开道具 UI」的直接条件是 `PropSelectionConfirmed=false`。
