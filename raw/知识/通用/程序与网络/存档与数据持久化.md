# 存档与数据持久化

> 来源：`raw/docs/ai/2026-06-08_离线存档架构重构.md`  
> 官方依据：`raw/docs/wiki/进阶内容/存档/20052_玩家数据存档.md`、`raw/docs/api/class/和平全局接口/角色系统/UGCPlayerStateSystem.md`

---

## 一、核心难点

玩家退出时存档会遇到四类问题：

1. **属性读取全 0**：Pawn 销毁时属性组件已清理，`GetGameAttributeValue` 返回 0。
2. **Pawn 与 Controller 互查失败**：销毁阶段 `GetPlayerControllerByPlayerPawn` / `GetPlayerPawnByPlayerController` 返回 nil。
3. **脚本变量与蓝图变量丢失**：Lua 表和 `ULuaMapHelper` 蓝图变量随 Pawn GC 回收。
4. **Controller 侧数据未持久化**：需要跨局保存的解锁数据必须单独存档。

---

## 二、解决架构：分离存档 + 属性缓存

```
Pawn 销毁     → SendModeCustomEvent("PlayerExitGame", self)     → SavePlayerArchive(Pawn)      ← 属性存档
Controller 销毁 → SendModeCustomEvent("ControllerExitGame", self) → SaveControllerArchive(PC)  ← 蓝图/业务数据存档
```

两条链路互不依赖，各自在自己的 `ReceiveEndPlay` 中发事件、存自己的数据。

属性靠**模块级缓存**兜底：在 `ReceiveBeginPlay` 注册 `AddGameAttributeChangedDelegate`，回调中把最新值写入脚本顶层 `local PlayerAttributeCache`，销毁时直接读缓存而不读组件。

---

## 三、七条设计原则

1. **模块级 `local` 变量是唯一不会被 GC 的存储**，属性缓存与全局状态都放在脚本顶层。
2. **销毁阶段不看对方实体**，Pawn 与 Controller 各存各自数据。
3. **登录时可以互查**，`ReceiveBeginPlay` 中 Pawn ↔ Controller 查询正常可用。
4. **闭包捕获 UID**，属性变化回调中用闭包持有 `playerUID`，不要在回调里通过 `AttributeOwner` 反查。
5. **`self.Player` / `self.Controller` 类型固定**，蓝图 Action 面板配置什么就传什么，不做类型探测。
6. **存档合并读取**：`GetPlayerArchiveData` → 修改 → `SavePlayerArchiveData`，不要覆盖他人写入的字段。
7. **每次对外 API 调用都用 `pcall` 保护**，见 [日志与错误保护规范](../工具与流程/日志与错误保护规范.md)。

## 四、涉及 API 与端侧

| API | 调用端 | 用途 |
| --- | --- | --- |
| `UGCAttributeSystem.AddGameAttributeChangedDelegate` | 双端 | 注册属性变化监听 |
| `UGCAttributeSystem.RemoveGameAttributeChangedDelegate` | 双端 | 注销监听 |
| `UGCAttributeSystem.GetGameAttributeValue` | 双端 | 读属性 |

## 六、V2 背包物品的跨局开关 ShouldPersist（2026-09-17，官方 API + 项目实测）

**结论：V2 背包「某个 ItemId 跨局保不保留」由物品 Handle 蓝图 CDO 上的 `ShouldPersist` 决定，不由 Lua 决定。**
排查「只有某几个道具跨局消失、其他正常」时，先查这个开关，不要先去写存档兜底。

**官方依据**：`raw/docs/api/class/和平全局接口/物品与背包/UGCBackpackSystemV2.md` 的
`GetBackpackPersistData(Player, ContainsNoPersist)`，参数说明为
「true: 包含**不持久化物品**数据, false: 仅包含持久化物品数据」⇒ 官方按物品区分是否持久化。

**开关位置**：`ShouldPersist` 是 `UGCBattleItemHandleBase` 的 `bool [Edit]` 属性，
继承链 `UGCBattleItemHandleBase → CommonBattleItemHandleBase → BattleItemHandleBase → ItemHandleBase`。
**它不在 `UGCBattleItem` 表的列里**，只能通过物品 Handle 蓝图（`ItemHandlePath` 指向的 `_C`）读写。

读取（MCP 纯查询，无需 plan）：

```python
import unreal_engine as ue
from unreal_engine.classes import DataTable, Blueprint
dt = ue.load_object(DataTable, '/<项目>/Asset/Data/Table/UGCBattleItem.UGCBattleItem')
rows = dt.data_table_as_dict()
hp = rows['<ItemId>'].as_dict()['ItemHandlePath']   # 是 dict，取 hp['AssetPathName']
cls = ue.load_class(hp['AssetPathName'])
print(cls.get_cdo().ShouldPersist)
```

写入（CDO 写，走 PRV：`ue_plan_submit` → `ue_py`）：

```python
cls = ue.load_class(base + '.Name_C')
cdo = cls.get_cdo()
cdo.ShouldPersist = True
ue.load_object(Blueprint, base).save_package()   # 必须保存，否则只在内存
```

`ue.schema:<Handle_C 路径>` 可列出该 Handle 全部可编辑属性（含 `ShouldPersist`、`TimeLimit` 等）。

**实测（pet_paradise，78 行）**：38 行 `ShouldPersist=True`、38 行 `False`。
被玩家报「跨局丢失」的卡正好都在 False 组：等级经验卡大/中/小、完美打工卡、扫荡卡；
打工翻倍卡与粪便清理卡等活动卡本来就是 True。
**多个 ItemId 可以共用同一个 Handle 蓝图**（如 3 行扫荡卡共用 `SDK`），改一次即全部生效；
同理，同名文件可能分布在不同目录（`SkillItem/clean` 与 `WorkItems/Base/clean` 是两个资产），
**必须按完整路径定位，不要按文件名**。

**注意**：`ShouldPersist=False` 组内还有全部枪械、金币、改名卡等——这些通常是「官方刻意不跨局保留」的，
不要顺手全改成 True。改之前先确认该道具是否真的需要跨局。

## 八、读档结果不可信时禁止用默认值落盘（2026-09-24，官方 API + 项目实测）

**结论：`GetPlayerArchiveData` 返回空表不必然代表“新玩家”。** 在 PIE/DS 启动早期，分块存档可能仍在异步拉取；若此时直接用默认初始值构造运行时数据并调用 `SavePlayerArchiveData`，会把默认值当成真实存档覆盖落盘。项目侧必须区分“服务端确认无存档”和“本次读取失败/尚未就绪”，后者不得进入正常业务结算，也不得保存。

**官方依据**：

- `raw/docs/wiki/进阶内容/存档/20052_玩家数据存档.md`：`GetPlayerDataSize` 返回玩家当前存档数据的总字节大小，包含所有分块数据量；**无数据时返回 0**。`GetPlayerArchiveData` / `SavePlayerArchiveData` 生效范围均为服务器。
- `raw/docs/wiki/进阶内容/存档/20460_PIE 本地存档.md`：PIE 启动时若 UID 槽位留空，该 UID 会进入「待拉取列表」，DS Ready 后由 DS 主动推送；运行中加入的新客户端也有「待上传队列」，说明存档同步是异步链路。

**推荐守卫**：

1. 读档后先判断玩法存档键是否存在且非空。
2. 若玩法键缺失，再调用 `UGCPlayerStateSystem.GetPlayerDataSize(uid)`：
   - 返回 `0`：服务端明确无存档，允许按新玩家初始化。
   - 返回大于 `0`，但 `GetPlayerArchiveData` 读不到玩法键且总表也为空：判为拉取失败，拒绝进入本局。
   - 接口调用失败或无法得到数值：判为状态未知，保守拒绝，不要猜测为新玩家。
3. 若总存档中已有其他玩法键但本玩法键缺失，可按“首次创建本玩法存档”处理，不能误判为整表拉取失败。
4. 保存层再加一道防线：运行时记录本玩家是否允许首次创建；读取结果不可信时 `SavePlayerArchiveData` 必须直接拒绝，并记录 `ArchiveNotLoaded` 一类错误码。
5. 拉取失败不要只“拒绝落盘后继续玩”：本局金币、仓库与结算都以错误默认值为基础，应在登录/初始化阶段明确失败并打印拒绝原因。

**验证边界**：该守卫依赖 `GetPlayerDataSize` 在分块拉取失败时仍能反映服务端已有数据。若该接口同时返回 0，则仍无法与真正新玩家区分，需要结合 PIE 选档流程或上层同步状态进一步处理。
