# Oasis 开发记录

将一次功能开发或问题修复整理成可复用、可核对的项目记录。记录必须以实际对话、文件、差异、官方文档、项目记录和日志为依据，不得用猜测补齐事实。

## 触发与范围

- 当用户消息包含 `（记录）` 时触发；也可在用户明确要求生成 oasis-skill-plus 开发记录时触发。
- 输出目录固定为 `D:\oasis-skill-plus\docs\ai`。技能安装目录是全局技能目录，不改变输出目录。
- 默认记录当前任务涉及的功能和修复；不要把无关历史内容写入文档。

## 取证顺序

1. 先回看当前对话中所有可见的功能点、问题现象、用户约束、修改决定、实际命令输出和已改文件。对话中没有提供或无法恢复的内容列为“缺失信息”，不得虚构。
2. 检查项目实际文件：读取相关 Lua、蓝图脚本、组件脚本和相关 `_JsonOutput` JSON；使用 `git status`、`git diff` 或文件时间与搜索结果确认修改范围。JSON 只能只读查看和校验。
3. 涉及绿洲 API、Lua 生命周期、蓝图 JSON、组件、事件、RPC、PIE、热更新、端侧限制或参数语义时，先使用 `$oasis-official-docs` 查证。无法确认的内容写明“暂不确定，需要进一步查证”。
4. 涉及 oasis-skill-plus 项目经验时，检索 `D:\oasis-skill-plus\docs\ai`、`docs\skills` 等项目记录；社区资料使用 `$sq-skill` 作为补充证据，明确标注其为社区经验而非官方结论。
5. 涉及日志、报错、崩溃、运行异常、PIE 失败或客户端/DS 差异时，继续使用 `$ugc-log-bug-analyzer`。没有日志就明确写“没有可用运行日志，以下仅为静态检查或推测”，不得伪造运行证据。

## 文档结构

按以下顺序创建 Markdown，并保留六个必需章节：

1. `功能概述`：用一段话说明目标、范围和最终行为。
2. `已实现功能`：用要点列出具体能力、端侧分工、事件/RPC/资源关系和验证结果。
3. `完整代码示例`：直接复制项目实际代码。每个代码块第一行标注 `-- 脚本: 实际文件名` 或使用 Markdown 标题标注文件名；嵌入完整函数或完整逻辑段，连同必要注释、分支和错误处理。不得只写路径、伪代码、调用摘要或“见某文件”。
4. `遇到的问题`：每个问题写清上下文、触发条件、可见现象、影响范围和证据来源，并区分日志事实、静态观察和推测。
5. `解决方案`：按问题逐项对应，直接写入修改后的完整代码或可复用方案；涉及多个脚本时分别嵌入完整逻辑段，说明端侧、调用链和验证方式。
6. `关键经验`：总结可迁移的命名、端侧安全、生命周期、日志、JSON 校验、RPC 和验证规则。

可在必需章节前后补充“证据与查证”“验证结果”“生效方式”“缺失信息”，但不要用这些章节替代六个必需章节。

## 代码嵌入规则

- 代码必须来自当前项目实际文件或当前对话中明确给出的最终代码；先读原文，再复制，禁止凭记忆重写。
- 以完整函数、完整事件处理器、完整 RPC 分发函数或能独立解释问题的完整逻辑段为最小单元，避免孤立几行。
- 保留原始脚本文件名、函数名、注释和关键日志。可在代码块外添加说明，但不得把外部文件路径当作代码替代物。
- Lua 示例遵守项目约定：变量带简短中文注释，函数带中文功能/参数/返回值注释，关键逻辑有 `ugcprint`，日志包含脚本名和函数名、入参、`self`、`HasAuthority`、关键变量、分支和错误上下文。
- 涉及端侧逻辑时明确写出 `if self:HasAuthority() then ... else ... end`，不要记录静默 `return` 作为解决方案。
- 涉及 RPC 时记录实际 `CF_KHDRPC`、`CF_FWDRPC` 分发路径和调用方向，不要把业务 RPC 添加到 `UGCPlayerController` 的直接函数中，除非实际代码和官方依据都明确支持。

## 文件命名与写入

- 文件名使用 `YYYY-MM-DD_功能名称.md`，功能名称取自本次任务，清理 Windows 不允许的字符；若同日同名已存在，追加短后缀而不覆盖已有记录。
- 使用 UTF-8 Markdown 写入 `D:\oasis-skill-plus\docs\ai`，写入前确认目录存在，写入后立即重新读取全文。
- 禁止使用“详见 XX 文件”“代码在 XX 路径”“见某文件”等外部指向来代替代码。代码和解决方案必须完整出现在本文档中。
- 不要把 `_JsonOutput` JSON 直接编辑进项目；如需记录 JSON，只读摘录相关字段并说明校验结果。

## 验证清单

写入后逐项检查并在文档或最终回复中如实报告：

- 文件存在于固定输出目录，文件名含日期和功能名，原有同名记录未被覆盖。
- 六个必需章节齐全；功能点、问题、方案和代码彼此对应。
- 每个代码块都有脚本文件名，并包含完整函数或完整逻辑段；代码与实际文件当前内容一致。
- 文档没有用外部路径替代代码，没有把推测写成日志事实，没有遗漏已知修改文件。
- 对 Lua 做语法/闭合/变量/API 引用静态检查；只能将实际执行的命令报告为运行验证，不能把静态检查说成 PIE 成功。
- 涉及蓝图、组件、资源、挂载或端侧加载时机时，记录“需要重新调试 PIE”；仅修改已加载 Lua 普通函数体才可记录“可尝试热更新”；无法确认时记录“建议重新调试 PIE”。不要自行扩大生效结论。
- 有缺失信息时，在文档中明确列出缺失项，并在最终回复中直接询问用户补充；不要制造虚假的问题、代码、日志、文档查证或验证结果。

## 最终回复

说明生成的绝对文件路径、核心内容、查阅的官方文档/项目记录/JSON/日志证据、验证方式与结果、缺失信息和生效方式。区分“已读取”“已执行”“已回读验证”和“需用户确认”。如果没有修改项目代码，不输出不存在的 PIE 或热更新成功结论；预估日志必须明确标注为“预估成功日志”。
