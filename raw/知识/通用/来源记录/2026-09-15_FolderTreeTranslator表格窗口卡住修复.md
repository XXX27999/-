## 一、报障

「工具的表格连接编辑器与回写功能卡住。」——点「连接编辑器」/「回写编辑器」后界面像卡死：
按钮永久变灰、状态栏停在「正在…」，不弹任何错误框；编辑器侧正常无报错。

| 步骤 | 做法 | 结果 | 结论 |

| 1 | 服务层直连实测（连接 / `get_schema` / 读表 / 写增 / 写删） | 1.81 / 0.30 / 0.35 / 1.08 / 0.75 s，写后回读一致（`回写成功并回读一致（329 行）`） | 排除 MCP 与写入链路 |

| 4 | 隔离探针：Tk 跨线程 `after` 三通道对比 | 见下表 | 定位到根因 |

### 2.1 隔离探针结论（`probe_thread_after.py`）

| 通道 | 结果 |
| --- | --- |
| 工作线程里 `win.after(0, cb)` | 抛 `RuntimeError('main thread is not in main loop')`，**不派发** |
| 工作线程里 `root.after(0, cb)` | 同样抛异常，**不派发** |
| `queue.Queue` + 主线程 `after(30)` 轮询消费 | **正常派发** |

## 三、根因

1. **主因（线程不安全）**：`_run_async` 的完成回调写成工作线程里的 `self.after(0, finish)`。
   CPython + Tk 直接抛 `RuntimeError`，异常发生在工作线程内且不在 `try` 覆盖范围内，
   线程被静默打死 → **所有 MCP 结果被丢弃、按钮永久禁用**。
   windowed 打包后 stderr 不可见，所以现场没有任何报错痕迹。
   （主线程内发起的 `after` 计时器是好的，容易误判成「只是慢」。）
2. **次因（漏复位）**：`_check_pie_state.done` 非错误路径未调 `_busy(False)`，
   而 `_run_async` 自身也不复位 → 连接成功后按钮永久 disabled，
   表现为「连上了但点不动」。即使修好主因，这一条仍会复现卡住。

## 四、修复（1.5.1）

| 项 | 内容 |
| --- | --- |
| 线程安全派发 | 新增 `TableEditorWindow._ui_post()`（主线程直接执行 / 工作线程压队列）与 `_poll_ui()`（主线程 30ms 轮询消费）；`_log` / `_set_status` / `_busy` / 完成回调全部改走 `_ui_post` |
| 统一兜底复位 | `_run_async.finish` 在 `on_done` 之前无条件 `_stop_ticker()` + `_busy(False)` |
| 任务代次隔离 | `_task_seq` 自增，回调只在代次一致时生效；中止或新任务发起后旧回调被丢弃 |
| 等待期反馈 | 状态栏每秒刷新「`<当前步骤>` ｜ 已等待 N 秒，编辑器繁忙（PIE 启动 / 编译 / 保存）时会排队」 |
| 中止能力 | 新增「中止」按钮；`UgcMcpClient.close()` 追加 `_wake_all_waiters()`，关连接同时立即唤醒在途请求，使其以 `McpConnectionError` 立刻返回（不依赖 socket 关闭能否打断 `readline`） |

## 六、可复用结论

1. 任何 tkinter 工具，工作线程**绝不能**调用 `after` / 控件方法 / `StringVar.set()`，
   一律走「队列 + 主线程轮询」；否则症状是线程静默死亡 + 界面假死，且难以发现。
2. 阻塞型任务的界面复位必须由**调度层统一兜底**，不能依赖每个回调自觉写。
3. 长等待要有「已等待 N 秒 + 中止入口」，才能把「偶发慢」和「真卡死」在主观看感上分开。
4. 排查「卡住」时先分层排除（服务层 → 打包层 → 界面层），避免直接怀疑 MCP。

## 七、未验证

1. 「中止」的能力边界：`close()` 唤醒的是工具侧的等待；若 `ue_py` 已送达编辑器并开始执行
   （例如已进入 `save_package()`），编辑器侧会继续跑完，工具只是不再接收结果，
   **不保证回滚半完成状态**。中止恰好发生在 save 中途时的表现待测。
2. 冻结窗口自检 exe 只覆盖界面调度层，未覆盖冻结环境下的真实 MCP 往返
   （冻结版 CLI 读表此前已单独验证 rc=0）。
