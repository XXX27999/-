## 1. 需求与最终结构

需求（用户原话要点）：

1. 每个主题用**独立文件夹**存放其 UI 控件图片素材，同一控件在不同主题文件夹中**文件名一致**；
2. 切换主题时，先**按主题名定位文件夹**，再**以控件名称为索引**查找并加载同名素材，完成控件主题替换；
3. 制定统一的资源命名规范（主题文件夹命名规则 + 控件文件名规则）；
4. 整理并迁移已有素材以适配新结构，同时**完整保留并重建已有 UI 图片索引**。

关键澄清（用户原话）：

- 「当前的品质只是占位」→ 15 个品质键是占位层，真主题是风格主题；
- 「要根据当前UI控件的实际图片素材」→ 迁移取控件当前真实素材，不用占位品质贴图；
- 「当前主界面，竞拍界面，结算界面当前所有边界图片用的图片素材就是一个主题」→ 三界面现有边界素材**合起来即一个完整主题**，故结构定为**两层**（`<StyleTheme>/<SlotKey>`），**不做每材质一份拷贝**。

```
Asset/TuPian/Dress/
└── <StyleTheme>/              风格主题目录（DefaultGray 已落地）
    └── <SlotKey>.uasset       控件素材，同名跨主题复用
```

路径模板（`Dress.Theme.PathTemplate`）= `Asset/TuPian/Dress/<Style>/<Slot>`；未来扩三层时改为 `<Style>/<Material>/<Slot>`，**控件文件名不变**。

## 4. 新增 / 修改的脚本

### 4.1 新增 `Script/Function/AuctionDressThemeService.lua`（初版 24394 字节 / 341 行；续跑后 27810 字符，新增接口见 4.4）

职责：按主题名定位文件夹 → 以槽位名索引同名素材 → 加载并替换控件画刷。对外接口：

| 函数 | 作用 |
|---|---|
| `GetRootPath` / `GetPathTemplate` / `GetDefaultStyleId` | 读主题目录与默认风格（均带代码回退值） |
| `IsFallbackEnabled` / `IsCacheEnabled` / `IsSlotDetailLogEnabled` | 读三个开关 |
| `GetStyleIds` / `GetSlotKeys` / `GetStyleDisplayName` / `IsValidStyleId` | 主题与槽位枚举、中文名、合法性校验 |
| `BuildSlotPath(styleId, slotKey)` | 用 `PathTemplate` 拼 `Asset/TuPian/Dress/<Style>/<Slot>` |
| `LoadSlotTexture(styleId, slotKey)` | `GetUGCResourcesFullPath` → `UE.LoadObject`；命中缓存直接复用；缺失回退 `DefaultGray` |
| `ResolveTargetWidget(widget, name)` | 先取 `widget[name]`，再 `GetWidgetFromName`，命中后回填字段 |
| `ApplySlot(widget, styleId, slotKey, targetName)` | 单槽位应用；控件或素材缺失即打分支日志并返回 false |
| `ApplyStyle(widget, styleId, slotTargets)` | 批量应用，返回 `allOK / appliedCount / totalCount` |
| `PreloadStyle` / `SetCurrentStyleId` / `GetCurrentStyleId` / `ClearCache` | 预热、当前风格状态、缓存清理 |

画刷替换按可用性依次尝试：UImage 两参 `SetBrushFromTexture(texture, false)` → UBorder 单参 `SetBrushFromTexture(texture)`；
两者都不可用则打「控件不支持」分支日志退出（不静默跳过）。

缓存键为 `styleId → slotKey`，缺失槽位写 `false` 作负缓存，避免反复 `LoadObject` 失败。

### 4.4 加载时序修复（同日续跑）

**首次 PIE 暴露的真问题**：主题服务逻辑本身正确，但主界面/竞拍界面的 `Initialize` 由 widget `Construct` 触发，**早于** `AuctionConfig.LoadDressConfigTable`。实测两轮分别早 **129ms**（10.32 轮）与 **142ms**（10.43 轮），表现为 `GetUiSlotTargets` 的槽位**全部**因「DressControlTable 值为空串」跳过，`themeAppliedCount=0 themeTotalCount=0`，而同一帧稍后配置装载日志是 `success=true appliedCount=18`（当时只装了控制表）。这不是数据问题，是**顺序问题**，且不报错。

修复（三处，通用范式详见[界面初始化早于配置表装载与惰性应用](../../知识/通用/UI与交互/界面初始化早于配置表装载与惰性应用.md)）：

| 文件 | 改动 |
|---|---|
| `AuctionConfig.lua` | `LoadDressConfigTable` 出口写模块级装载标记 `AuctionConfig.DressConfigLoaded` / `DressControlLoaded`（每次以最新结果覆盖，失败置 false 让 UI 继续等待），并补进出口日志 |
| `AuctionDressThemeService.lua` | 新增 `IsDressControlLoaded()`；新增 `ApplyStyleToHostUIWhenReady(hostWidget, uiKey, stateKey)`：未就绪则按 `waitFrames` 节流打日志并空转等待，就绪后**只应用一次**，把「完成标记 / 上次应用的主题 / 等待帧数」三个字段写在 widget 自身上（不持有界面引用）；另加模块内局部 `GetCurrentStyleSilently()` + 默认主题缓存，保证每帧调用的快速路径既不读表也不打日志，同时保留「主题变化自动重应用」能力 |
| `AuctionHubUIService.lua` / `AuctionTestUIService.lua` | `Initialize` 末尾的直接应用改为调惰性入口（多数返回「等待中」并落一条分支日志）；各自 `Tick` 顶部（在节流刷新之前、`Initialized` 为真时）每帧调一次，用 `pcall` 保护并印错误 |

同时确认了后续刷新不会覆盖主题画刷：`AuctionHubUIService` 内**没有任何** `SetBrush*`；`AuctionUITextureReplacementService.Refresh` 全工程无调用方；`AuctionTestUIService` 唯一的 `SetBrushFromTexture`（1018 行）属于仓库藏品图，不在主题槽位目标内。故「一次性应用」不会被后续刷新冲掉。
