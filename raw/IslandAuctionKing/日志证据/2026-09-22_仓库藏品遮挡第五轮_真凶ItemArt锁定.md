# 仓库藏品遮挡 第五轮：真凶 `ItemArt` 锁定

## 摘要（一句话）

单格 `CollectibleCodexItemUI_C` 内的 **`ItemArt`**（`UBorder`，无贴图，`BrushColor` 深灰 **A=1.0**，
`Pos(18,12) Size(224,141)`，是 `ItemContent` 的**最后一个**子控件 → 压在全部兄弟之上），
因**未勾选 `bIsVariable`** 导致 Lua 侧取不到、`ApplyCellChrome` 折叠不了 →
一块不透明遮罩长期盖住单格主体（含 `ItemImage`）。
**已勾选 `bIsVariable` 修复，PIE 实测 `ItemArt=Collapsed`，`unreachable=[]`。**

## 0. 本轮目标

用户指定排查方向：「**底格控件内部自带不透明层** 先走这条」。

即：在「`ScrollBox` 滚动时重排 draw order」与「底格控件内部自带不透明层」两条待查方向中，
先走后者（可离线查蓝图，不必等 PIE）。

## 1. 结论摘要

| 项 | 结论 |
|---|---|
| **真凶** | 单格控件 `CollectibleCodexItemUI_C` 内部的 **`ItemArt`** |
| 形态 | `UBorder`，**无贴图**，`BrushColor = (0.16, 0.17, 0.18, **A=1.0**)` —— 完全不透明深灰 |

### 现象机制（最终解释）

`ItemArt` 是一块 **224×141 的不透明深灰遮罩**，且位于单格内部**最上层**。
它盖住的正是单格自己的主体区域（`ItemImage` 在 `Pos(44,46) Size(168,168)`，完全被 224×141 覆盖）。
→ 用户看到的「格子」观感，其实来自这块遮罩；藏品图在它下面，因此**看起来永远被「格子」压住**。
因为它在单格内部而不是画布层级，所以此前所有针对 ZOrder / 覆盖层迁移 / 裁切的修复都无效。

## 2. 两条引擎事实（本轮新发现，**推翻通用 UE 认知**）

### 2.1 【决定性】`ESlateVisibility` 枚举与标准 UE4 **对调**

活体枚举实测（探针 `[E1]`，客户端日志 `_dkck7pqy1yl5bf`）：

```
ESlateVisibility: Visible=0  Collapsed=1  Hidden=2  HitTestInvisible=3  SelfHitTestInvisible=4  ESlateVisibility_MAX=5
```

| 名称 | 本引擎 | 标准 UE4 | 差异 |
|---|---|---|---|
| `Visible` | **0** | 0 | 同 |
| `Collapsed` | **1** | 2 | **对调** |
| `Hidden` | **2** | 1 | **对调** |
| `HitTestInvisible` | 3 | 3 | 同 |
| `SelfHitTestInvisible` | 4 | 4 | 同 |

**影响**：任何「读 `Visibility` 返回值判断状态」的代码，按标准 UE 序号判读会**把 `Collapsed` 误判成 `Hidden`**。
枚举**名**（`ESlateVisibility.Collapsed`）仍可用，只是数值是 1 而非 2。

### 2.2 `GetWidgetFromName` 只挂 UUserWidget 根控件

| 调用对象 | 结果 |
|---|---|
| `AuctionTestUIWidget:GetWidgetFromName('CollectibleCodexItemUI_C_0')` | ✅ 返回活体单格 |
| `AuctionTestUIWidget:GetWidgetFromName('WarehouseContentCanvas')` | ✅ 返回画布 |
| `AuctionTestUIWidget:GetWidgetFromName('ItemArt')` | ❌ `nil`（非本控件成员）|
| `CanvasPanel:GetWidgetFromName(...)` | ❌ `property not exist` |
| `Button:GetWidgetFromName(...)` | ❌ `property not exist`（`[C4] colon/dot 双形态均 `attempt to call a nil value``）|

引擎日志原文：

```
LuaExtend_GetProp: LuaExtend::Lua_GetPropertyValue Failed:
Object [CanvasPanel ...WarehouseContentCanvas] PropName [GetWidgetFromName]: property not exist
```

**推论**：`FindNamedWidget(cellWidget, name)` 的「回退控件树按名查找」**恒失败**，
且每次失败刷一整段 LuaException —— 是「84 格卡 76 秒」的机制之一。

## 7. 方法学教训（第三次固化）

1. **探针先确认对象是自己以为的那个再读值。** 本轮两次探针选错对象（`CellButton01` 是 Button、`AuctionCellButtons[1]` 是 ItemButton），
   导致「9 项全 NIL」的假象，浪费一轮推断。
   确认手段：读日志里 `ud_object[...]` 的完整路径，不要只看变量名。
2. **「按字段名 + 按接口名」两路都失败时，先查蓝图里该成员是否存在，再下「无效」结论。**
   `ItemArt` 的根因不在代码，而在 `bIsVariable` 没勾 —— 这是纯静态事实，**用 `ue_py` 读活体即可确证，不必等 PIE**。
3. **凡涉及引擎枚举/绘制机制，先活体取枚举值，不要套用通用 UE 认知。**
   `ESlateVisibility` 对调就是典型反例。
4. **JSON 镜像会过期，活体读数才权威。** 本轮的 `mtime` 是前一天 16:29，
   据它推断出「`NameFrameImage`/`ItemImage` 未勾选」是错的（活体都是 `True`）。
   下「属性缺失」结论前先比 `mtime`（镜像 vs uasset）。
5. **读 `Slot` 尺寸要区分「自己的 slot」与「父级继承的 slot」。**
   `ItemArt` 从 JSON slot 读成 256×268，活体实测是 `Pos(18,12) Size(224,141)`。
   **几何以 `ue.widget_inspect` 为准。**
6. **「子控件顺序 = 绘制顺序」是定位内部遮挡的第一抓手。**
   `ItemArt` 是 `ItemContent` 的**最后一个**子控件 → 必然压在所有兄弟之上。
   单格内部遮挡**不必查 ZOrder**，直接看控件树顺序即可。
