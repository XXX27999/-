# 仓库藏品覆盖层 19..32 未迁移与 UI 同名行冲突（2026-09-22）

用户在 2026-09-22 10:24 重启 PIE 后复报：**藏品图片与藏品信息图片仍固定在仓库格子下面**。

先排除「上一轮修复没进包」：本地 `Script/Function/AuctionWarehouseCellService.lua` 30889 B 与 PIE 实际运行的打包副本
`ShadowTrackerExtra\Saved\UGCLinuxDebug\IslandAuctionKing\Script\Function\AuctionWarehouseCellService.lua`（10:24:38）**字节一致**，

## 2. 真根因（双证）

### 2.1 覆盖层扫描范围被配置回退值截断

同一批日志：

```text
【AuctionTestUIService+ValidateWidgetContract】关键数据 fixed=42 gridSlots=84 collectibleSlots=18 propSlots=8 ...
【AuctionWarehouseCellService+EnsureOverlays】入口 ... slotCount=18 attached=nil
【AuctionWarehouseCellService+EnsureOverlays】关键数据 movedCount=36 missingCount=0
```

蓝图 `AuctionTestUI.json` 实证**实际存在 32 组**覆盖层：

```text
CollectibleImage numbers=[1..32] max=32
CollectibleButton numbers=[1..32] max=32
CollectibleLabel  numbers=[1..32] max=32
```

→ `slotCount=18` × 2（Image+Button）= `movedCount=36`。**19..32 共 42 个控件（14 图 + 14 钮 + 14 信息文本）从未迁入
`WarehouseContentCanvas`，也从未被折叠**，永久停留在舞台画布原位；而 `ApplyScrollGeometry` 已把滚动框 slot 抬到
`baseCellZOrder=10`，滚动框内的 84 个背景格因此把它们整片盖住 —— 即「藏品图与藏品信息图固定在仓库格子下面」。

旁证：整个会话（两份 LuaLog）检索 `Collectible(Image|Button|Label)(19|2x|3x)` **命中 0 次**，
说明 19..32 从未被任何一次刷新触碰。

### 2.2 `UI.CollectibleSlotCount` 同名行双源冲突

DataTable 回读（`ue_py` + PRV）：

| 表 | 行 | 值 | 行内说明（原文摘要） |

| `Asset/Data/Table/Customized/UI/UIConfigTable`（329 行） | `UI.CollectibleSlotCount` | **32** | 「竞拍界面藏品显示槽数量；需不小于 Gameplay.Warehouse.MaxItems……」+「蓝图中必须存在对应数量的 CollectibleImageNN/CollectibleButtonNN/CollectibleLabelNN 控件（**当前 32 组**）」 |

加载时序（同一客户端）：

```text
[10.26.12.231] AuctionGlobalConfigTableService.LoadAndApplyConfig  [UI.CollectibleSlotCount] 新值: 18 setOK=true
[10.26.12.305] AuctionUIConfigTableService.LoadAndApplyConfig      rowName=UI.CollectibleSlotCount value=32 setOK=true
```

两条结论：

2. **UI 初始化时整个 `UI.*` 子树尚未就绪**：本会话共 **68 条**点号路径、**443 次** `AuctionConfig+Get 中间节点不是table`
   失败（一级命名空间分布 `UI` 61 / `RoundHistory` 3 / `Gameplay` 2 / `InfoPanel` 1 / `PropSelection` 1），
   全部回退默认值 —— `Initialize` 早于 `AuctionConfig.LoadFromTable`（后者 10:30:06 才成功）。

### 2.3 全量核查：大表 51 条 `UI.*` 的重复面

只读比对两张表全部行（`ue_py`）：

```text
legacy_total=150 legacy_UI_rows=51
uiTable_total=329
duplicated=2 valueDiffers=2 valueSame=0 onlyInLegacy=49
```

- **真正重复且值冲突的只有 2 行**（删 `UI.CollectibleSlotCount` 之前统计）：

  | 行 | 遗留大表 | `UIConfigTable` |
  |---|---|---|
  | `UI.SettlementWarehouse.OriginOffsetX` | 24 | 40 |
  | `UI.SettlementWarehouse.OriginOffsetY` | 158 | 146 |

  行内说明给出判据：`UIConfigTable` 侧写明「切图替换后默认 36」（Y 为 250）+「与结算切图像素对齐。依赖：AuctionSettlementUI」，
  遗留侧只是通用模板注释（「影响 UI 槽位或布局……」，切图前旧值）。
  → **权威值 = 40 / 146；而大表加载在后，实际生效的是过期值 24 / 158**，属同一类同名行双源冲突（结算仓库偏移与切图不对齐）。

- 其余 **49 条 `UI.*` 仅存在于遗留大表**（`UI.TestWarehouse.*`、`UI.InfoCard.*`、`UI.Codex.Texture.*`、`UI.SettlementReveal.*` 等），
  `UIConfigTable` 并无对应行。这类行**不能直接删**——删了就彻底失去配置、只能吃 Lua 默认值；
  正确做法是「先抄进 `UIConfigTable` 对应域 → 回读确认 → 再删大表行」的迁移流程。
  这也解释了 §2.2 中 `UI.TestWarehouse.*` 读取失败：**不是时序问题，而是行本来就不存在**（一直吃 Lua 默认值）。

## 3.5 复报后的决定性定位：绘制顺序 = 子控件插入顺序，而不是 ZOrder 数值（2026-09-22 第二轮）

用户复跑 PIE 后报告**问题依旧**。据此反推排除了「残留覆盖层」作为主因：

- 本轮已把两张表的 `UI.CollectibleSlotCount` 统一为 **32**，且 Lua 回退默认值也改成 **32**
  → 无论配置是否就绪，`uiConfig.collectibleSlotCount` 都是 32
  → `EnsureOverlays` 必然扫 1..32、`movedCount` 应为 64、`NormalizeOverlaySlots` 的 `surplusFound` 应为 0。
- 既然残留覆盖层已不存在，画面却仍表现为「藏品图压在格子下面」，说明**覆盖层与格子的相对绘制顺序本身是错的**。

**机制（关键）**：本引擎画布的**绘制顺序 = 子控件插入顺序，后插入者盖住先插入者**；
对 Slot 调 `SetZOrder` 只改数值，**不会翻转既有绘制顺序**。依据三条：

1. 官方 API 页 `raw\docs\api\class\Others\UCanvasPanelSlot.md` 对 `SetZOrder` 仅描述 “Sets the z-order on the slot”，没有任何重排语义。
2. 项目自身实测记录 `raw\IslandAuctionKing\日志证据\2026-09-16_竞拍仓库藏品占格重叠日志分析.md` 已写明
   「藏品按 `itemPosition` 顺序绘制，slot12 晚于 slot1 默认压在上层」。
3. 连续三轮（09-16 补 ZOrder、09-21 重申 ZOrder=40、09-22 每帧重申 ZOrder）都没能改变遮挡关系，与「ZOrder 不重排」一致。

**错误顺序**：原流程是 `EnsureOverlays`（把覆盖层迁进滚动内容画布）→ `EnsureCells`（再建 84 格并挂进同一个画布）
→ 格子后插入，绘制在覆盖层之上 → 覆盖层永远压在格子下面，且随内容一起滚动，表现为「固定」在格子下方。

**修复**：

1. `AuctionTestUIService.Initialize` 调换顺序：**先 `EnsureCells`，再 `EnsureOverlays`**。
2. 新增 `AuctionWarehouseCellService.BringOverlaysToFront(widget)`：对 1..`overlayScanLimit` 的
   `CollectibleImageNN` / `CollectibleButtonNN` 执行 `RemoveFromParent` → `AddChildToCanvas` → `SetZOrder(40)`，
   把覆盖层强制排到画布末尾；并在摘除前读取 Slot 的位置/尺寸、重挂后原样恢复，避免首次刷新前闪位。
   - **只重挂 Image/Button，不重挂 `CollectibleLabelNN`**：Label 是按钮的子控件，摘除会把文本从按钮里拽出来。
3. `Initialize` 在 `EnsureOverlays` 之后立即调一次 `BringOverlaysToFront`；
   `RefreshWarehouse` 首次刷新时再用 `AuctionWarehouseCellService` 的顺序标记（`AuctionWarehouseOverlaysOrdered`）重申一次，
   防止 Initialize 之后有其他服务往画布追加控件打乱顺序。

> 注意：这一条仍属**基于证据的机制推断**（官方文档未正面描述重排行为，无法在离线端证伪），
> 但它是唯一能同时解释「三轮 ZOrder 修复全无效」的机制；`SetZOrder(40/10)` 保留为双保险，
> 因此即使该推断有误、画布其实是按 ZOrder 排序的，修复也不会引入回退。

## 4. 顺带修掉的性能缺陷（同类根因）

`ApplyCellChrome` 原「递归遍历内容面板 + 按控件类折叠」在本引擎**完全失效**：

```text
【AuctionWarehouseCellService+ApplyCellChrome】关键数据 控件树清单=(),(),(),(),(),(),(),(),(),()
```

## 6. 关键经验（可迁移）

1. **画布绘制顺序 = 子控件插入顺序，后插入者在上；`Slot:SetZOrder` 只改数值、不翻转既有顺序。**
   要改变遮挡关系必须改「挂载顺序」（先挂底层、后挂上层），或把上层控件 `RemoveFromParent` 后重新 `AddChildToCanvas`。
   连续三轮（09-16、09-21、09-22）只改 ZOrder 而无效，是本次最贵的教训，见 §3.5。
2. 「按 N 循环处理蓝图控件」的 N 必须取自**蓝图实际存在的控件清单**，不能只信配置值 —— 配置在 UI 初始化阶段常未就绪，会静默回退默认值，导致超出默认值的控件既不被处理也不被折叠。
3. 同名配置行分布在「遗留大表」与「按域专表」时，**后加载者胜**；必须核对加载时序，不能只看某一处取值。
4. `pcall` 只能阻止错误外抛，**不能阻止引擎记录异常与堆栈**；在未知子控件上探测不存在的成员是性能陷阱。
5. 客户端 `Clientlog`（`LuaLog`/`FullLog`/`TagLog`）在 PIE 会话进行中恒为 **0 B，只有该客户端退出时才落盘**；
   进行中唯一实时可读的是 DS 侧 `DSlog\FullLog\*_realtime.log`，但客户端 `ugcprint` 不会进那里，
   `doluastring` 的回显也不会进编辑器日志 → 需要客户端证据时必须等会话结束。
6. 判断「上一轮修复到底有没有进到运行的包」：比对本地 Lua 文件字节数与
