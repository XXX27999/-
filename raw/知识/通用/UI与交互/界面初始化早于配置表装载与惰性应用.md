# 界面初始化早于配置表装载与惰性应用

- 类型：通用知识（实测结论 + 可复用方案）
- 主题：绿洲 UGC 里 UI 控件 `Construct`/`Initialize` 早于 `UGCGameState:ReceiveBeginPlay` 的配置表装载，导致「读配置初始化界面」整段空跑；给出装载标记 + Tick 惰性应用的修复范式
- 适用范围：所有用 DataTable 驱动 UI 初值的绿洲 UGC 工程客户端展示层。服务端同样装载同名表（各自读本地表，无 RPC 同步），但服务端无 widget，不涉及本问题
- 证据状态：项目实测（PIE 客户端与 DS 双端 TagLog 命中同一时间线）
- 来源：IslandAuctionKing（海岛竞拍王）装扮主题接入，PIE DebugID `_dkck7pp6wwnk1n`（客户端日志时间 2026.09.20-10.43:45 起）；原始扫描输出见 `D:\知识库\和平精英绿洲起源\备份\IslandAuctionKing\20260918_DressTheme\timing_fix_scan.txt`。**第二实例（2026-09-20）**：同一界面接入「同名画刷」机制后复用同一范式，PIE DebugID `_dkck7pp6wwsxum`，日志可见 `ApplyStyleToHostUIWhenReady` 与 `ApplySameNameThemeToHostUIWhenReady` **各自独立**打 `waitFrames=1`、装载后各自 `applied=true`
- 更新时间：2026-09-20
- 关联主题：[配置表驱动开发](../配置表驱动开发.md)、[UGCAskQ MCP 实测陷阱清单](../工具与流程/UGCAskQ-MCP实测陷阱清单.md)、项目证据 [装扮主题索引与素材目录迁移](../../IslandAuctionKing/配置表/2026-09-18_装扮主题索引与素材目录迁移.md)、[同名画刷主题切换机制](../../IslandAuctionKing/配置表/2026-09-20_同名画刷主题切换机制.md)

## 1. 现象

UI 初始化里写了「读配置 → 应用」，日志显示：

1. `Initialize` 里读到的配置全是空串/回退值，命中「未定项跳过」「无已确定控件」等分支；
2. 同一帧稍后，配置表装载日志打印 `success=true appliedCount=N`；
3. 结果：**配置表本身装载成功，但界面初始化阶段整段空跑**，界面上看不到任何配置驱动的效果；
4. 不报错、不崩，只表现为「功能写了完全不生效」，极易误判成配置写错、控件名写错或 API 不可用。

## 2. 实测时间线（IslandAuctionKing，PIE DebugID `_dkck7pp6wwnk1n`）

| 时刻 | 事件 |
|---|---|
| 10.45.39.998 | `【AuctionHubUIService+Initialize】入口`（由 widget `Construct` 触发） |
| 10.45.40.004 | `【AuctionDressThemeService+ApplyStyleToHostUIWhenReady】分支 装扮控件表尚未装载，本帧跳过等待 uiKey=Hub waitFrames=1` |
| 10.45.40.146 | `【AuctionConfig+LoadDressConfigTable】出口 success=true appliedCount=107 invalidCount=0 dressConfigLoaded=true dressControlLoaded=true` |
| 10.45.42.326 | Tick 中重试命中：`【…+ApplyStyleToHostUI】入口`（配置已就绪） |
| 10.45.43.955 | `…ApplySlot 出口 success=true styleId=DefaultGray slotKey=HubBackground`、`出口 allOK=true appliedCount=1 totalCount=1` |

结论：本轮前后两次 PIE 分别测得 **UI 初始化早于配置装载 129ms 与 142ms**；两次顺序一致。DS 侧同表在同一次会话中装载成功（`appliedCount=107`），说明不是表或加载器本身的问题。

加载时机本身符合工程约定：配置表由 `UGCGameState:ReceiveBeginPlay` 在表系统准备完成后显式调用 `AuctionConfig.LoadFromTable` 装载，而 UI 控件的 `Construct` 由控件被创建时触发，二者**不在同一个时序点上，且 UI 在前**。

## 3. 为什么不能在 `Initialize` 里直接应用

- `Initialize` 的调用者是 widget 的 `Construct`，触发时机是「控件被创建」，早于 GameState 的表装载回调；
- 在 `Initialize` 里做「读配置 → 应用」，等价于对着尚未装载的表读取 → 拿到回退值；
- 即使把顺序改成「配置装载完再创建 UI」也不稳：UI 可能在等待阶段就被创建（本项目主界面在等待阶段即 `CreateAndShow`），而配置装载与 UI 创建分别由不同模块驱动，耦合两者会引入新的脆弱点。

## 4. 可复用方案：装载标记 + Tick 惰性应用

三步，缺一不可。

**第一步：装载方留下可查询的标记。** 配置加载函数在出口处把结果写到模块级字段，供 UI 侧查询（不要靠「配置值是否为空」反推，那会把「表里就是空值」误判成「还没装载」）：

```lua
-- 每次装载都以最新结果覆盖，失败置 false，让 UI 继续等待重试
AuctionConfig.DressConfigLoaded = configOK == true   -- 主题/文案表装载标记
AuctionConfig.DressControlLoaded = controlOK == true -- 槽位→控件映射表装载标记
```

**第二步：应用方提供「就绪后再应用」的惰性入口。** 状态落在 widget 自身字段上（不持有界面引用，界面销毁即随之释放）：

```lua
function Service.ApplyWhenReady(hostWidget, uiKey, stateKey)
    -- 1) 已按当前主题应用过 → 静默返回（每帧调用也无副作用，不读表不打日志）
    -- 2) 未就绪 → 记 <field>WaitFrames，只按帧数节流打日志，返回 false
    -- 3) 已就绪 → 应用一次，写 <field>=true 与 <field>StyleId=<当前主题>
end
```

- 快速路径里**不要调用带日志的公开接口**，否则每帧刷屏；用模块内局部函数静默解析当前值；
- 「当前值」写进 widget 字段，与待应用时比对 → 运行期换肤自动重应用，不需要额外的事件订阅；
- 表就绪后**只尝试一次**（含「该界面确实没有可替换项」「素材缺失」两种情况），否则会逐帧重复加载资源；
- 等待期的日志按 `waitFrames == 1 or waitFrames % 60 == 0` 节流。

**第三步：两个调用点。** `Initialize` 末尾调一次（立即尝试，多数会返回「等待中」并把意图打进日志），widget 的 `Tick` 里每帧调一次（重试到就绪为止）。

```lua
-- Initialize 末尾
local ready = Service.ApplyWhenReady(widget, "Hub", nil)
-- Tick 顶部（在节流刷新之前，保证重试频率=帧率）
if widget.Initialized == true then
    local ok, res = pcall(Service.ApplyWhenReady, widget, "Hub", nil)
    if not ok then ugcprint("【…+Tick】错误 … error=" .. tostring(res)) end
end
```

## 5. 判定与排错要点

- **判据**：同一帧内同时出现「读到的配置为空/回退」与「配置装载 success=true」，即可推定是顺序问题，不是数据问题；
- 先确认 widget 的 `Tick` 真的在被驱动——查 `Tick` 链路上的节流刷新日志条数与首末时间戳（本项目实测 549 条、跨 9 分钟连续），不要假设框架一定调了 `Tick`；
- `doluastring` 依赖「PIE 客户端已注册 Lua 控制台」，本机多轮 PIE 均报 `No PIE client window is registered with the Lua console`；此时以客户端/DS TagLog 作为唯一实证，不要用未注册的控制台重试当阻断理由；
- 修复后用日志三连确认：`waitFrames=1` 分支 → 装载 `success=true` → 就绪后 `allOK=true appliedCount>0`，且各计数应**恰为 1**（证明一次性语义生效、没有逐帧重复）。
- **判定次序陷阱（2026-09-20 实测，易静默失效）**：惰性入口的第一步判定必须是「**界面非空 → 表已装载 → 机制开关 → 快速路径 → 应用**」。若把「读机制开关」排在「判表已装载」之前，装载前就会去读 `Xxx.Enabled` 这类配置行，日志报 `【AuctionConfig+Get】错误 中间节点不是table path=...`，更糟的是**把「当前主题」也缓存成了空串**，此后每帧快速路径都命中缓存直接返回 → 机制永久静默不生效（PIE 第一轮 `_dkck7pp6wwstp8` 即此现象：`appliedCount=0` 且无该机制的 error）。同理，「读调试/全局开关」的代码必须放在 `if IsXxxLoaded() then` 之内。

## 6. 适用范围与边界

- 适用于一切「配置表驱动 UI 初值」的场景：贴图/画刷替换、槽位数量、布局坐标、文案；
- **不适用**于纯函数内的按需读取（例如点击时才读一次配置），那类读取天然发生在装载之后，无需惰性化；
- 服务的「当前主题/当前风格」这类全局状态若放在模块级局部变量，注意 `AuctionConfig` 的装载标记也是模块级字段——服务端与客户端各有独立 Lua 状态，各自读各自本地表，不需要也不应该做 RPC 同步；
- 若工程本身已有「配置装载完成回调」，优先用回调触发一次应用，惰性 Tick 作为兜底即可；本例没有该回调，故以 Tick 为准。

## 7. 待查证

1. 该顺序是否在**所有** UGC 工程都成立（只在 IslandAuctionKing 实测两次）；若某工程 `UGCGameState:ReceiveBeginPlay` 早于 UI 创建，惰性入口的 `Initialize` 首次调用即会成功，行为仍正确，故方案对顺序变化不敏感。
2. 表系统在客户端 PIE 下的就绪时刻与其他子系统（组件、事件绑定）的相对顺序未逐项测量，仅测了与 UI `Construct` 的相对顺序。
