## 1. 定位与合规边界

热度 / 评分 / 评论数**没有公开接口**，端内抓包已被判定为不可行且违规（私有协议加密 + ACE 反作弊封号 + 违反开发者协议，见关联主题第 8 节）。本工具是唯一保留的自动化取数路径：

- **只读截屏**，不改客户端、不注入进程、不需要 root；
- 「自动上滑」走 `adb shell input swipe`（用户手势层面模拟），默认关闭；参数是**幅度 35% 屏高 + 800ms**（旧值 55%/350ms 属快速甩动，惯性导致一次滑过一页多，2026-09-20 真机反馈后下调，见 6.6），界面上可现场微调；
  - **它是否可用由手机 ROM 决定，不由本工具决定**：小米/红米（MIUI / HyperOS）必须额外打开开发者选项里的「**USB 调试（安全设置）**」，否则 `input swipe` / `input tap` 会被 `SecurityException: ... INJECT_EVENTS permission` 直接拒绝（2026-09-20 真机实测，见 6.4）。工具把这条错误单独分类为 `inject_denied` 并给出对策；**本工具不使用 root / `sendevent` / `monkey -f` 事件脚本 / 注入框架**（无条件，不分场合）—— 它们属绕过 ROM 安全策略，与本工具红线冲突（见第 7 节首条）。
- 游戏界面若设置 FLAG_SECURE，截屏会得到黑图，工具会检测并提示改用拍照导入，**不得**因此转向 Hook 屏幕图层等手段。

## 3. 使用流程

1. **连手机**（adb 已装好并预填，跳过安装）：手机开 USB 调试（开发者选项 → 连续点版本号开启 → USB 调试），数据线连电脑，手机上点「允许 USB 调试」并勾选记住 → 工具里点「刷新设备」。
   - **要翻页就必须多开一个开关**：小米/红米（MIUI / HyperOS）在开发者选项里还要打开「**USB 调试（安全设置）**」（与「USB 调试」是两个独立开关；打开时会要求登录小米账号 + 插 SIM 卡并联网，提示「网络异常」时改用移动数据）。不开这个开关，截屏正常、但一切 `input` 模拟点击/滑动都会被 `INJECT_EVENTS` 拒绝。华为/荣耀对应「允许模拟点击」。
   - 若 `adb devices` 显示 `unauthorized`：拔插数据线，重看手机上的授权弹窗。
   - 若显示 `offline` 或空白：换 USB 口/数据线（部分线只充电）；Windows 通常免驱，装个手机厂商助手（华为 HiSuite / 小米助手）可补驱动。
   - 无线调试（Android 11+）：`adb pair 手机IP:配对码端口` 再 `adb connect 手机IP:5555`，工具暂未在界面上支持，需命令行先连好。
2. **截屏**：进入绿洲启元玩法大厅列表页 →「ADB 截屏」。
   - **截屏前先确认手机屏幕是点亮且已解锁的**：熄屏/锁屏状态下 `screencap` 会成功返回一张整幅纯色的图（真机实测，见 6.5），工具会提示「屏幕未点亮」——点亮重截即可，不用去拍照导入。
   - 无 adb 时可用另一台设备拍照后「导入图片/文件夹」，或 PrintScreen 后「粘贴剪贴板」。
3. **布局模式（关键）**：整页固定是 **2 行 × 3 列 = 6 张卡**，两种模式的差别只在「框从哪来」。
   - **大厅网格（默认，推荐）**：卡片框与字段框全部按第 4 节的实测几何自动生成，**不需要手工拖框**。参数行的「行数 2 / 行距 314 / 列数 3 / 列距 495」是真机实测值，误改了可点「按图重置布局」一键还原。
     - 若某字段位置与你的设备不符，可**直接在该字段上拖框**：会把框折算成「相对卡片左上角的偏移」并覆盖到整页每张卡（日志会打印折算结果）；「清空框选」可撤销全部覆盖。
   - **自选框选**：用于「大厅列表页之外」的页面或非常规分辨率。在第一张卡上依次拖好各字段，工具按 **列数 × 行数**（默认 3 列 × 2 行）配合「列距 / 行距（真机像素）」平移到整页。注意自选模式的框是**真机像素绝对坐标**，横向按 `col × 列距`、纵向按 `row × 行距` 平移；行列号会写进结果的「列 / 行」两列。
4. **校验**：点「试识别一张卡」，日志给出 `原始文本 → 解析值`，裁切图存 `crops\` 供人工核对；不准就调「OCR 放大」（默认 4，1~8 倍）。
5. **采样**：设间隔/次数 →「开始采样」。每次截屏自动识别、按地图名去重；勾选「自动上滑」可连续翻页。
   - **勾自动上滑之前先点一次「测一次滑动（量位移）」**（在「自动上滑」复选框右边）。它做四件事：截前帧 → 真滑一次 → 等惯性停下 → 截后帧 → 比对两帧**量出实际滚动了多少像素**，并给出「没滑够 / 合适 / 滑过头」判定和建议幅度。失败会在日志里直接给到「哪个 ROM 开关没开」，并自动把复选框取消掉。
   - **「测手动滑动」按钮（不用输入注入）**：截一帧后给你 5 秒在手机上手动上滑一次，再截一帧，量出**人手滑一页实际滚了多少**。用途：本机 `input swipe` 被 ROM 拒绝时仍能标定出「一页该滚多少」；也可反过来核对自动滑动的落点是否接近人手效果。
   - **上滑幅度/时长可现场微调**（采样区两个 Spinbox，会存进配置）：大厅列表是连续滚动，不同机型/列表的滚动阻尼不一样，**滑过头就调小「上滑幅度」、拉长「时长」**（默认 35% 屏高 + 800ms，从 55%/350ms 下调而来，见 6.6.2）   - **失败时的合规替代路径（不需要注入权限）**：不勾「自动上滑」，把「间隔」调大到够你手动滑一页（建议 8~15s），点开始采样，然后每截一张你就在手机上手动上滑一页。工具按间隔连拍 N 次，效果与自动翻页一致。
     - ⚠ 这条路径下**建议同时取消勾选「检测到列表末尾自动停止」**：它靠「连续两帧内容几乎一致」判定到底，手动滑太慢时会连拍两帧同一页而被误判成已到末尾、提前停止。
6. **导出**：三种格式，落 `out\`，含原始文本与换算后数值两套列。
   - **导出 Excel(.xlsx)**（2026-09-20 新增，推荐）：真·工作簿 —— 表头加粗、冻结首行、列宽自适应，`热度_值/评分_值/评论数_值` 按**数字**写入（可直接排序、求和、做透视），其余为文本。
   - 导出 CSV：`utf-8-sig`（带 BOM），Excel 双击直接开、中文不乱码。
   - 导出 JSON：UTF-8、中文不转义。
   - **「打开输出目录」**按钮：直接打开 `out\`，不用记路径。
   - 导出失败会**明确告诉你原因**：文件被 Excel/WPS 占用（先关闭同名文件）、缺少依赖（给安装命令）、其它异常（给异常类型）。旧版异常只打到 stderr，GUI 没有控制台，表现为「点了没反应」。

## 4. 大厅列表页布局标定（2026-09-18 逐像素实测）

**坐标基准**：用户提供的真机截图 1920×864 ≡ 程序内部视图 1078×468；`sx = 1.7811`、`sy = 1.8462`。代码里 `LOBBY` 一律写视图坐标，运行时换算成真机像素；换算**必须用 `round()` 不能用 `int()`**（见第 7 节）。

**卡片网格**（真机 px）：

| 项 | 实测值 | 视图坐标 |
|---|---|---|
| 三列边界 | (109,590) (603,1085) (1098,1580) | `col_x` = (61,331) (339,609) (617,887) |
| 第一行卡片顶 | y = 168（三列一致，y=168 处有单像素尖峰＝上边框） | `first_row_y` = 91 |
| 第一行卡片底 | y = 481（卡高 313） | `card_h` = 170 |
| 第二行卡片顶 | y = 482（行距 314） | `row_step` = 170 |

**一页就是一屏 2 行 × 3 列 = 6 张**（第三行卡顶会落到 y>864，超出屏幕，故一页只有两行）。对应的默认步长写在模块常量里，供「自选框选」模式使用，也保证界面上的默认数字与真机一致：

| 常量 | 值（真机 px） | 依据 |
|---|---|---|
| `INT_COL_STEP` | **495** | 三列卡左边界 604-109 与 1099-604 |
| `INT_ROW_STEP` | **314** | 第二行卡顶 482 − 第一行卡顶 168 |
| `INT_ROW_COUNT` | **2** | 一页两行 |

上表里「三列边界」的 x 起止在视图坐标下写作 `col_x = (61,331) (339,609) (617,887)`。列数由界面上的「列数」控制：大厅网格用它截取 `col_x[:n]`，自选框选用它决定横向复制几列 —— **两种模式共用同一个列数值**。

**字段框**（相对「卡片左上角」的真机 px；**两行共用同一套偏移**，这是本次标定的关键结论）：

| 字段 | 真机框 | 视图框 | 说明 |
|---|---|---|---|
| 热度 | (10, -4, 102, 40) | (5.6, -2.2, 57.3, 21.7) | 火苗图标右侧的数字+单位，如 `77.0万`；**必须原样识别，不加预处理**。生产读法另见第 7 节「多配方」 |
| 评分 | (126, -9, 205, 48) | (71.0, -5.0, 115.0, 26.0) | 星标**右侧**的数字，如 `4.1`；用 `sharp` 预处理。**左边界 v4 已从 112 右移到 126**，理由见下 |
| 地图名 | (4, 226, 312, 263) | (2.2, 122.4, 175.2, 142.5) | 标题大字 |
| 标签 | (4, 266, 300, 292) | (2.2, 144.1, 168.4, 158.2) | 标签小字（竖线分隔） |
| 入口按钮 | (342, 252, 480, 297) | (192.0, 136.5, 269.5, 160.9) | `下载` / `维护中` |

> **顶部两个数值字段是「流式排版」（2026-09-22 颜色连通块逐列量化，12 张卡）**：信息带里是「火苗 + 热度文本（宽度可变）→ 固定间距 → 星标 + 评分数字」，所以**星标与数字的 x 位置随热度文本宽度浮动** —— 实测星标起点 **54.5~65.7 视图**、评分数字起点 **75.8~82.0 视图**（同一页不同卡之间最大差 11 视图 ≈ 20 真机 px @1920）。这意味着固定的「评分框左边界 71」在部分卡上会切进星标右尾（→ 文本被污染成 `74.3`/`co4.5`）或落在数字前（→ 读空）。对策见第 7 节的「多配方 / 多左边界兜底」，**不要**改成「跟着星标右缘自适应」—— 星标与数字紧贴时右缘算不准，实测会把数字首位切掉（`3.6`→`36`、`4.3`→`3`）。
>
> **多配方读法的上下边界与字段框不同**：字段框的 y 范围（-2.2..21.7）是「窄框读法」的**最小可用高度**；多配方读法统一用**信息带高度 -7..32.5 视图**（含火苗与彩字上下沿）。混用会把彩字上沿切掉、读数退化（实测真机 `116万` 退成 `16万`）。

**本页不可用字段**：`评论数`。逐像素核查过顶部信息带，本页卡片上**只有火苗+热度、星星+评分**两组数字，没有评论数；因此标记为不可用直接留空，而不是给个错位框去读无关文字。**注意**：「不可用」是**本页**的属性，只在「大厅网格」模式下生效；切换到自选模式后该黑名单不生效，用户拖了框就照框读。

**几何版本守卫**：`GEOM_VERSION` 写进 `sampler_config.json`。启动时若存档版本与代码不一致，会把存档里的 `rects / row_step / card_h / ncol / card_count / card_step / col_step` 一并丢弃并回到按图实测的默认值，防止早期错误标定或已变语义的旧参数被静默复活。**任何改动 `LOBBY` 几何、或改动卡片网格语义（行数/列数/步长的含义）都必须把 `GEOM_VERSION` +1。** 当前为 **v4**（v4 = 评分框左边界右移：星标墨迹与评分数字**紧贴无间隙**，旧框把星标右半整块圈进来，星标右弧被 OCR 读成 `7`，产出 `74.3` / `?2.9`。v3 = 明确一页 2 行 × 3 列、列数两模式共用、新增列距 495、自选框选改为按行×列复制）。

> ⚠ **旧的「评分框左边界固定 112」结论已作废**（第 7 节里那条 2026-09-18 的坑记录保留原文作为历史，但结论以本节 v4 为准）。112 是按 1920×864 那张图按「星标 x≈91..110、数字 x≈112..170」定的；在 2400×1080 上按同样比例换算后，星标墨迹实际占到「相对卡左」约 137..165 真机 px、数字占 165..200，而旧框换算后是 140..250 —— **把星标右半（140..165）整块圈了进来**。星标是实心的，其右侧弧线被 RapidOCR 认成字符 `7`，于是 `4.3` 被读成 `74.3`、星标本身被认成 `?` 时读成 `?2.9`。**根因不是「框太小」，是「星标和数字之间没有间隙可切」**，所以只能右移把星标挤出框。

## 5. 解析规则（已实测）

- 单位换算：`万 ×1e4`、`亿 ×1e8`、`k ×1e3`；用 `Decimal` 计算，避免 `2.2亿 → 220000000.00000003` 这类浮点污染。
- 标签剥离：OCR 常把字段名一起读出，自动剥 `热度/热力/人气`、`评分/星级/分数/分`、`评论数/讨论数/评价数/评论/讨论/评价/留言`；顶部那行还会误读出 `★☆🔥△▲`，也一并剥掉。
- **字段级预处理**（`FIELD_PREP`）：只有 `评分` 用 `sharp`（自动对比度 + UnsharpMask）。实测**热度绝不能加预处理** —— 加了会把 `111万` 读成 `川1万`，值差 100 倍。
- **多档投票**（`read_field`）：数值字段在一个小阶梯（基础倍率 ±1、+2）上各读一次再投票 —— 优先「带单位」的读法，其次取众数，同票优先带小数点的。这不是过度设计：RapidOCR 对**同一张裁切图跨进程结果会抖动**（实测同一框不同次运行读出 `111万`/`川1万`、`4.4`/`A2`）。
- **字段级解析器**（`FIELD_PARSERS`，2026-09-20 新增）：默认走通用 `parse_number`，`评分` 改走 `parse_score` —— **形态匹配**：`(\d)\.(\d)` 取**最后一个**匹配（真值在星标右侧，被星标带出来的误读字符必然贴在它左边）；`10.0` 单独特判；**没有小数点就返回 `None`，不猜**（`36` 不再被拆成 3.6，也不会像旧通用解析那样把 `36` 解析成 36 然后被区间拦下）。这是「抗星标污染」的第二道防线，第一道是框的位置。
- **区间校验**（`FIELD_VALID_RANGE`）：`评分` 限 (0, 10)。越界值**不写入数值列**，但原始文本照常保留供人工复核（评分常把小数点读丢：`3.6 → 36`）。
- 越界框返回 `None` 并跳过，**不静默补黑边**（避免产生脏数据）。
- 黑屏检测：灰度极差 < 8 判为纯色/黑屏 → 提示该界面禁止截屏。
- **卡片状态 vs 丢弃**：封面未加载完的卡**仍然输出**，只是打「下载中」标记；完全无文字（地图名与热度都空）才真正丢弃。日志分别报「丢弃 N 个」与「标封面未加载 M 个」，两者不混算。

### 6.5 真机截屏通路与黑屏成因判定（2026-09-20）

```
adb shell dumpsys window     → mCurrentFocus=NotificationShade   ← 停在锁屏/通知层
adb shell dumpsys activity   → ResumedActivity=com.dragon.read  ← 后台是别的应用
```

→ 黑屏成因是**屏幕熄灭/锁屏**，**不是 FLAG_SECURE、更不是工具缺陷**。

**据此修掉一处会误导用户的文案（本轮改动）**：旧版只要检测到纯色就一律提示「界面可能禁止截屏（FLAG_SECURE），请改用拍照导入」。但真机最常见成因是屏幕熄灭 —— 此时正确做法是**点亮屏幕后重截**，「拍照导入」是错误建议。新增：

- `Adb.screen_awake()`：读 `dumpsys power` 的 `mWakefulness`，返回 `(True/False/None, 原始值)`；`None` = 读不出（不猜）。
- `explain_blank(adb)`：把纯色截屏分成三种成因并各给对策 ——
  | mWakefulness | 判定 | 给出的对策 |
  |---|---|---|
  | 非 `Awake`（如 `Dozing`） | 屏幕未点亮 | **先点亮屏幕并解锁，再重新截屏** |
  | `Awake` | 屏幕亮着却纯色 | 该界面很可能 FLAG_SECURE → 改拍照导入 |
  | 读不出 | 不猜 | 先确认屏幕已点亮；仍全黑才是禁截屏 |
- 三处调用点（「ADB 截屏」按钮、`detect_page_state`、`grab_with_retry`）全部改为走 `explain_blank()`。

**真机端到端**：

```

screencap 成功: size=(1080, 2400) mode=RGB
is_blank = True
explain_blank() 实际给出: 截屏为纯色，且手机屏幕当前未点亮（mWakefulness=Dozing）
                        ——先点亮屏幕并解锁，再重新截屏。
```

**自检新增 F 段**（常驻防回归）：`is_blank` 对纯色/有内容分别返回 True/False；`explain_blank` 在「熄屏 / 亮屏 / 读不出」三种输入下给出**三套互不相同**的对策，并断言「熄屏」文案里不出现 `FLAG_SECURE`、「亮屏」文案里不出现「点亮屏幕」——防止两种成因再次被混为一谈。

### 6.6 真机采样复现：评分误读 `74.3` / `?2.9` 与上滑「滑过头」（2026-09-20）

用户在同一天用真机跑出一份采样结果，提出两个问题：① 自动上滑**滑过头**（一次跨过一页多）；② 评分是 0–10 分，却出现 `74.3` 与 `?2.9`。两个都定位到了根因并修掉。

#### 6.6.1 评分误读：星标墨迹与评分数字**紧贴，无间隙可切**

**取证方式**（只读，全部在已存截图上做）：对评分所在的横向条带做 OCR，把每个识别 token 的文本与其 x 区间打出来，分别在 **1920×864** 与 **2400×1080** 两张真机图上交叉核对。

| 图 | 星标墨迹占比（相对卡左，真机 px） | 评分数字占比 | 旧评分框换算后覆盖 |
|---|---|---|---|
| 1920×864 | ≈ 91..110 | ≈ 112..170 | 112..200（勉强避开星标） |
| 2400×1080 | ≈ 137..165 | ≈ 165..200 | **140..250（把星标右半 140..165 整块圈进来）** |

结论：**星标右缘与数字左缘之间没有空白间隙**，任何想完整覆盖数字的框都必然带进一小条星标。旧框在 1920 上侥幸避开，在 2400 上就踩中了 —— 星标是实心图形，RapidOCR 把它的右侧弧线认成字符 `7`（→ `74.3`），把整个星标认成 `?`（→ `?2.9`）。这也解释了为什么误读值总是「真值左边多一个字符」：`7` 和 `?` 都长在真值左侧。

**修复（两道防线）**：

1. **框**：`评分` 框左边界从视图 62.9 右移到 **71.0**（真机 112 → 126@1920），把星标挤出框，只留约 7px 星标尾。`GEOM_VERSION` 升到 **v4**，旧存档几何自动作废。
2. **解析**：新增 `parse_score()` 形态匹配（见第 5 节），`(\d)\.(\d)` 取**最后一个**匹配，没有小数点就返回 `None`。这样即使星标残留带出一个字符，真值仍能取对（`74.3 → 4.3`、`?2.9 → 2.9`）。

**为什么两道都要**：只调框，遇到不同 DPI / 不同卡面排版仍会漏进星标；只加解析器，会把「完全没小数点」的脏读也照收。**框负责不让它进来，解析器负责万一进来也读对。**

**验证**：自检新增 **G 段**（常驻防回归）——
- G1 单元：`4.4/4.3/4.5/2.9/3.6` 正常值、`★4.3`（带星标）、`74.3`→4.3、`?2.9`→2.9、`3.67`→3.6、`10.0`→10.0、`A2`/`36`/`食24`/空 → `None`，共 14 个用例全通过；
- G2 端到端：真机截图 `shots/shot_20260920_143400_001.png` 6 张卡逐张走真实 OCR 链路，命中 **6/6**（4.4 / 4.3 / 4.3 / 2.9 / 4.5 / 3.6）。

#### 6.6.2 上滑「滑过头」：连续滚动列表 + 快速甩动惯性

大厅列表是**连续滚动**（页面底部常露出半个第三行），一屏不是一个固定单位。原默认 **幅度 55% + 时长 350ms** 在 Android 上属于「快速甩动（fling）」手势：手指抬起后列表仍按惯性继续滚，实际位移远大于手指位移，于是一次跨过一页多。

**修复**：幅度降到 **35% 屏高**、时长拉到 **800ms** —— 位移更小、按压更久，手势语义从「甩动」变成「拖动（drag）」，惯性项大幅衰减，落点可控。同一台 2400×1080 机器换算后：

```
旧: shell input swipe 1200 842 1200 248 350   (594px / 350ms)
新: shell input swipe 1200 842 1200 464 800   (378px / 800ms)
```

同时在采样区新增两个可调参数（**上滑幅度(屏高比)** / **时长(ms)**，会存进配置），并在旁边写明「滑过头就调小幅度、拉长时长」—— 不同机型 / 不同列表的滚动阻尼不一样，**不存在一个放之四海皆准的值，只能给保守默认 + 现场微调**。参数构造抽成纯函数 `swipe_args(w, h, percent, duration, display)` 便于单测。

**验证**：自检新增 **H 段**（常驻防回归）——断言新默认幅度落在 0.10~0.50、时长落在 400~2000ms、位移比旧默认**更短**、时长比旧默认**更长**、起点为屏幕中线 / y=78%、`-d` 参数位置正确。结果通过。

> ⚠ 自检 H 段第一版写错下标（`old_args[2+5] - old_args[2+3]` 实际算的是 `duration - x`，不是 y1−y2），且断言 `new_args[2:4] == ["shell","input"]` 也取错了位置 —— 都是「按固定下标取参数」的典型翻车。已改为按 `"swipe"` 关键字定位取 `(x, y1, y2, duration)`。**给 adb 参数数组写断言时不要写死下标。**

**回归**：自检 A/A2/B/C/D/E/F/**G**/**H** 全通过；`test_regress.py` 仍 **26/30**、卡片定位 6/6，评分列由「2/6 + 1 个假值」变为「3/6 正确 + 0 假值」，其余字段无退化。

#### 6.6.3 「测试滑动」升级为量化测量：只看「通过 / 失败」等于没自检（2026-09-20）

用户反馈：「**测试滑动不会实际滑动，不方便测试滑动幅度**」。查下来是两件事叠在一起：

1. 旧版 `test_swipe` 只判定 `input swipe` 的**退出码**，成功就打一句「滑动自检通过：设备允许输入注入」。它**确实发出了滑动**，但日志里没有任何「滑了多少」的信息 —— 用户看不到效果，也就没法据此调幅度；
2. 若该机 `input swipe` 被 ROM 拒绝（见 6.4），按钮直接失败、根本不滑，「测幅度」这条路径完全不可用。

**改法：把「能不能滑」升级成「滑了多少」。**

| 组件 | 作用 |
|---|---|
| `measure_scroll(前帧, 后帧)` | 纯函数。多块模板匹配 + 中位数投票，估计两帧间**内容向上移动了多少像素**（返回原图像素值）。**最佳匹配不显著优于次优时返回 `None`** —— 宁可说「测不出」，也不硬给一个错数 |
| `swipe_advice(手指位移, 实际滚动, 页高, 幅度)` | 纯函数。按「实际滚动 / 一页高度」判 `没滑够(<0.7)` / `合适(0.7~1.3)` / `滑过头(>1.3)`，并**按比例反推建议幅度** |
| 「测一次滑动（量位移）」 | 截前帧 → 滑一次 → 等 `SWIPE_SETTLE_SEC=1.0s` 让惯性停下 → 截后帧 → 量位移 → 报判定与建议幅度 |
| 「测手动滑动」 | 截前帧 → 等 `MANUAL_MEASURE_WAIT=5s` 让你手动滑 → 截后帧 → 报人手滑一页的实际滚动像素。**不依赖输入注入**，ROM 拦了也能用 |

日志形态（自动模式）：

```
自动滑动：手指位移 378px（幅度 35% × 屏高 1080）｜实际滚动 512px（占屏高 47%）
判定：滑过头 —— 实际滚动 512px ≈ 1.2 页…建议把「上滑幅度」调到 0.29、或拉长「时长」后再测一次。
提示：把「上滑幅度」改成 0.29 后再点一次本按钮复测；惯性是非线性的，建议复测 1~2 次收敛。
```

**为什么必须等惯性停下再截**：甩动手势抬手后列表还会继续滚，立刻截屏量到的是中间态，会低估位移。

**「一页」怎么算**：一页 = 2 行卡片；行距 `INT_ROW_STEP=314` 是在 1920×864 下标定的，按屏高等比换算（`row_px = 314 × 屏高 / 864`），故 `page_px = 2 × row_px`。

**验证**：自检新增 **I 段**（常驻防回归）—— 合成两类图各 5 档已知位移（0/40/120/300/520px）：
- **噪声纹理**（非周期，任何偏移唯一匹配）：5/5 精确命中；
- **卡片列表**（周期排版、但每行封面色与地图名不同，模拟真实列表）：5/5 精确命中 —— 证明**周期错位不会被误判成真值**；
- 无关两帧必须返回 `None`（不得硬给数）；
- `swipe_advice` 五个分支（没滑够 / 滑过头 / 合适 / 测不出 / 几乎没动）判定与建议幅度方向正确。

**回归**：自检 A/A2/B/C/D/E/F/G/H/**I** 全通过；`test_regress.py` 仍 **26/30**、卡片定位 6/6，无退化。

## 7. 已知坑

- **纯色截屏不等于「界面禁截屏」（2026-09-20 真机修正）**：`is_blank()` 只能判定「是不是纯色」，**判定不出成因**。真机实测：手机 `mWakefulness=Dozing`（熄屏/锁屏）时 `screencap` 会成功返回一张合法但整幅纯色的 PNG（1080×2400，仅 7,935 B）。旧版只要纯色就提示「界面可能禁止截屏（FLAG_SECURE），请改用拍照导入」—— **熄屏场景下这是错误建议**，正确做法是点亮屏幕重截。现由 `explain_blank(adb)` 按 `dumpsys power` 的 `mWakefulness` 分流：非 `Awake` → 提示点亮屏幕；`Awake` 却纯色 → 才是 FLAG_SECURE 走拍照导入；读不出 → 不猜，先让用户确认亮屏。**新增黑屏文案时不要再绕开 `explain_blank` 自己拼字符串。**
  - 连带结论：`screencap` 与 `input` 不同命 —— **截屏（读帧缓冲）不需要注入权限，熄屏时也能成功返回**；只有 `input swipe|tap` 这类注入才被 ROM 拦。所以「上滑失败」时截屏取数这条路仍然通（只是要人手点亮屏幕、手滑翻页）。
- **`input swipe` 被 ROM 拒绝 ≠ 工具坏（2026-09-20 真机定案）**：小米/红米 MIUI / HyperOS 下 `adb shell input swipe|tap` 会抛 `SecurityException: ... INJECT_EVENTS permission`（exit 255）。**先排除、别乱改代码**：① 看 `adb shell am get-current-user` 是否为 0（不是 0 说明在分身/副用户下，切回主用户）；② 看 `settings get global adb_enabled` 是否为 1；③ 以上都正常就只剩「USB 调试（安全设置）」没开（小米/红米专有，需插 SIM 卡 + 登录小米账号 + 联网；华为/荣耀为「允许模拟点击」）。诊断顺序与真机取证见 6.4。
  - ⚠ **本工具不使用 root / `sendevent` / `monkey -f` 事件脚本 / 注入框架**（无条件，不分场合）。社区里确实流传「`monkey -f` 能绕过 HyperOS 的 `input` 限制」，但那是**绕过 ROM 安全策略**，与第 1 节的合规红线直接冲突，本工具一律不做。合规解法只有两条：打开上述开关，或不勾自动上滑、改手滑。
  - 该开关**无法通过 adb 只读方式确认状态**（`settings list global|secure`、`getprop` 均未暴露；实测见 6.4 的取证表）——属**待查证**，不要凭猜测断言用户「已经开了」。唯一可靠的确认方式是看 `input swipe` 的退出码（工具里的「测试滑动」按钮即此）。
- **手动上滑替代路径有个静默陷阱**：不勾「自动上滑」改手滑时，如果「检测到列表末尾自动停止」还开着，而你的手速慢于「间隔」，工具会连拍到两帧同一页 → 命中「连续两帧内容一致」→ **提前判定到底并停止**，看起来像「翻页失败/只采到一页」。手滑前先把「间隔」调到 8~15s，并取消勾选「检测到列表末尾自动停止」。
- **`wm size` 有两个值时取最后一个**：`Physical size` 是硬件分辨率，`Override size` 才是当前生效分辨率（本机 1440×3200 vs 1080×2400，两者差 1.33 倍）。取错会让滑动坐标与截屏尺寸不匹配。`screen_size()` 已改为取最后一个匹配。
- **「一页 2 行 3 列却只能框选一列」的三个来源（2026-09-20 全部修复）**：
  1. `draw_all_rects` 只按行距**纵向**复制，还把大厅模式的「相对卡片偏移」当成绝对像素画 → 画面上永远只有一列框，看着像工具只支持一列；
  2. `card_boxes`（自选模式）只按卡片步长向下复制、`col` 硬编码为 0 → 识别时右边两列整列丢失；
  3. `ncol`（列数）早期只属于大厅网格，**被设成 2 时大厅模式就真的只认两列**，而界面上没有任何提示。
     现在：画布用与识别同一套网格绘制（所见即所识别）、自选模式按「行数 × 列数」复制、列数两模式共用且默认 3；`GEOM_VERSION` 升到 v3 会自动清掉旧存档里被改坏的列数。
- **大厅网格模式下拖框曾被静默忽略（2026-09-20 修复）**：旧版把框原样存进 `self.rects`，但识别取的是 `LOBBY` 几何，用户拖了框既不生效也不报错。现在大厅模式下拖框会折算成「相对卡片左上角的偏移」覆盖到整页每张卡，并在日志打印折算结果；「清空框选」可撤销全部覆盖。
- **字段可用性不能用 `self.rects` 判断（2026-09-20 修复）**：`recognize_card` 旧版以 `self.rects.get(f)` 判断字段有没有框。用户在大厅模式下存过几个手工框后，`self.rects` 只剩那几项，「入口按钮」等没有手工框的字段会在**大厅模式下也被无条件留空**。已改为按模式判定（大厅看 `LOBBY`/覆盖/rects 三者之一）。
- **评分框不要并入星标（2026-09-20 重写结论）**：星标墨迹与评分数字**紧贴无间隙**，任何覆盖全部数字的框必然带进一小条星标；星标是实心的，右侧弧线会被 OCR 认成 `7`、整个星标会被认成 `?`，于是产出 `74.3` / `?2.9`（误读字符恒在真值**左侧**）。
  - 2026-09-18 的旧结论「左边界固定 112」**已作废**：那是按 1920×864 单张图定的，换到 2400×1080 按比例换算后，旧框覆盖了星标右半（相对卡左 140..165），直接踩坑。现左边界为 **126@1920（视图 71.0）**，`GEOM_VERSION` v4。
  - 只调框不够：星标残留时仍会带字符，故加第二道防线 `parse_score()` 形态匹配（取最后一个 `\d.\d`，无小数点返回 `None`）。**框负责不让它进来，解析器负责万一进来也读对** —— 改评分相关逻辑时两条都要保住，自检 G 段会拦。
  - 反过来也别把框收得太狠：收窄会切掉数字左半，同样读错。判据是「框内应只剩数字、没有星标的实心块」。
- **换算不能用 `int()` 截断**：`int(108.6) = 108`，这 1px 偏移足以让顶部那行淡字整块读不出来（实测：改 `round()` 后 c3r2 热度才读出 `111万`）。`find_cards` 与 `field_rect` 两处都必须 `round`。
- **字段框高度要给足**：热度框真机高 44px 才带得上单位「万」（收到 40px 只回 `77.0`，差 1e4 倍）；按钮框要 45px 才读全 `下载`（收到 30px 只剩 `载`/`力`）。收窄的失败是**静默的**——只少一个字符，不报错。
- **自动上滑「滑过头」是惯性，不是步长算错（2026-09-20 真机）**：大厅列表是**连续滚动**（底部常露出半个第三行），一屏不是一个固定单位。默认 **35% 屏高 + 800ms**；原来的 55%/350ms 属「快速甩动」，抬手后列表靠惯性继续滚，一次跨过一页多。判断手势性质的经验值：**位移小 + 时长长 = 拖动（惯性小）**，位移大 + 时长短 = 甩动（惯性大）。不同机型/列表的滚动阻尼不一样，**不存在通用值**，滑过头就调小幅度、拉长时长（界面上两个 Spinbox 直接可调，会存进配置）。构造参数走 `swipe_args()` 纯函数，别在调用点手拼数组。
- **按钮回调里的异常必须接住（2026-09-20「结果无法导出为表格」的成因之一）**：GUI 程序没有控制台，回调里抛出的异常只打到 stderr，用户看到的就是**「点了没反应」**。最典型的是导出时目标 CSV 正被 Excel 打开 → `PermissionError`。现在统一走 `_do_export()` 外壳：空表提示、`PermissionError` 提示先关文件、`ImportError` 给出安装命令、其它异常打印类型与消息。**新增按钮回调时照抄这个外壳。**
- **导出要 Excel 就得有 xlsx，不能只给 CSV（2026-09-20）**：用户说的「表格」就是 Excel 工作簿，而工具原本只有 CSV/JSON，且 `.venv` 里没装任何 xlsx 库。现新增 `write_xlsx()`（openpyxl：表头加粗 + 冻结首行 + 列宽自适应 + 数值列写数字）与「导出 Excel(.xlsx)」按钮；CSV 保留（utf-8-sig 带 BOM，Excel 双击可开）。
  - ⚠ **类体里的 `COLS = EXPORT_COLS` 是在类加载时求值的**：导出列常量必须定义在 `class App` **之前**，放到文件末尾会 `NameError: name 'EXPORT_COLS' is not defined`（2026-09-20 实测踩到）。写文件的函数可以放末尾（运行时才调用），常量不行。
- **自检只报「通过 / 失败」等于没自检（2026-09-20 用户反馈）**：`test_swipe` 旧版只看 `input swipe` 退出码，成功就打一句「允许输入注入」。用户看到的是「通过」，却**不知道滑了多少**，也就没法据此调幅度 —— 表现为「测试滑动好像没实际滑动」。凡「参数需要现场标定」的自检，必须输出**可比较的量化结果**（这里是实际滚动像素 + 判定 + 建议值），不能停在布尔值。
  - 配套：**量位移前必须等惯性停下** —— 但**固定 `sleep(SWIPE_SETTLE_SEC=1.0s)` 已被取代**（2026-09-21）：惯性衰减时长每次都不同，固定等待量到的是中间态，正是「每次距离都不一」的主因。现改为 `wait_scroll_stop()`：轮询截屏直到连续两帧位移为 0（4s 兜底）。
  - 被 ROM 拦住的机器上也要能标定 → 「测手动滑动」按钮走**前后帧比对**，不用输入注入。
- **「精确滑动」只能靠闭环，开环调参调不出精确（2026-09-21）**：`input swipe` 是**开环**的 —— 抬手瞬间的速度估计、列表阻尼、惯性衰减都不可控，同一组参数必然给出不同落点，**不存在**「算准一次就准」的参数（minitouch / `sendevent` / `monkey -f` 这类注入方案属第 1 节红线，不做）。可行的是三条：① **闭环补齐**（工具已实现、默认开）：滑一次 → 等停 → 量实际 → 按本轮实测增益 `gain = 实际/手指` 反推补第二次（最多 3 轮），误差收敛到 ±12%；② **拖动模式**（开环里最准）：时长 1200~2000ms + 小幅度，实际≈手指位移，方差最小；③ **不要求精确 —— 采样场景的正解**：只要「每次 ≤ 一页」，重叠由「按地图名去重」吸收、末尾由「连续两帧一致」判定，**宁可少滚不要跳过**，所以调参目标应是「略小于一页」而不是「正好一页」。增益只记内存不落盘（换页面/换机型就失效）。
- **「只滚一页却测不出位移」是顶部固定区造成的（2026-09-21 重写测量算法）**：`measure_scroll()` 旧版对所有块求「同一位移下的中位残差」，隐含假设**整屏内容一起移动**。但大厅顶部有一条约占屏高 **19.4% 的固定区**（页签/标题，`LOBBY` 卡顶 168/864），不随列表滚动 —— 位移一大，列表里的块被拿去跟**顶部固定区**比，残差被整体抬高，最佳与次优几乎并列（真机失败样本比值 **0.96 / 0.98**，全部被判「测不出」）。现改为**逐块投票**：块只取自列表区（`LIST_TOP_RATIO=0.20`）、候选位移不得落进固定区、每块自己投一票后按位移聚类取最大簇；另有三条配套：上方块够不到大位移时**弃权**（否则被截断的边界值会成假票）、**同票比残差**（卡片列表有固定行距，`真值` 与 `真值±行距` 都能对上，票数会打平，但别名对上的是别的卡片、残差更高）、**质量闸门**（残差/失配基线 > 0.55 判 `None`）。真机 4 对成对截图：修前 2 对测不出，修后 3 对量出（526 / 516 / 151px），第 4 对因相隔 76s、封面重绘被质量闸拦下（0.60）——**拦下是对的**，宁可说测不出也不给假值。
- **等滚停的假性超时**：`wait_scroll_stop()` 原来只在循环头判「是否超时」，而截屏 + 比对本身要 0.3~1s，实测一路跑到 **4.9~5.1s**（上限写的是 4.0s），日志里全是「仍未停稳」的假警报。改为每轮比对**之后**再判硬截止，并把「停稳」放宽到 `位移 ≤ 2px`。
- **「每次测出的滑动距离都不一样」是两类成因，处理方式完全不同（2026-09-21）**：
  1. **测量时机错（可修的 bug）**：滑完固定 sleep 就截屏 → 惯性没跑完，量到中间态，而衰减时长每次不同。修法：`wait_scroll_stop()` 轮询到两帧一致（4s 超时兜底）。**采样循环同样要等**：原来只靠「间隔」兜底，间隔调到 0.5s 时下一帧是在滚动途中截的，表现为「翻页忽多忽少 / 同一页被截两次」。
  2. **对象本身随机（只能如实呈现）**：Android fling 的落点本身就是随机变量，**单次测量不是事实**。修法：连测 3 次（界面「连测次数」1~5）取**中位数**，并由 `summarize_runs()` 同时报出极差与稳定性判定（极差/中位数 ≤15% 稳定、≤35% 一般、>35% **不稳定**）；「不稳定」档明确写「单次测量不可信」并给「时长拉到 1200ms+、让手势变拖动」的对策。**不要用取平均把方差抹掉** —— 用户需要的是知道这个值能不能信。量不出的那次（`None`）从统计里剔除，不能拉低中位数。
- **要根治「测不准」，靠实时流 + 帧链积分，而不是继续调两帧比对（2026-09-21）**：`screencap` 实测 **2.11s/帧（≈0.5fps）**，只够抓「滑前 / 滑后」两帧 —— 位移一大重叠区就太小 → 匹配失败；量到的还是某一瞬间的**中间态**。改用 `adb exec-out screenrecord --output-format=h264 -` 连续取帧（本机实测 **24~27fps**），位移就可以**沿帧链逐段积分**：每段只有几 px~几十 px（真机实测最大单段 4px），必然匹配得上，总和即这一滑的完整真实位移，**与惯性衰减快慢、什么时候停无关**。
  - 真机对照（97277e5f，横屏 2400×1080，幅度 0.35 / 时长 800ms，各 3 次）：**两帧比对 = 114 / 1284 / 1284px**（极差比 0.91 → 「不稳定」）vs **帧链积分 = 666 / 678 / 594px**（极差比 0.13 → 「稳定」）。同样的滑动、同样的参数，差别只在量法。
  - 三个实现细节：① ffmpeg 解管道流**不要加 `-probesize` / `-analyzeduration`**，实测解出 0 帧；② 存帧统一降到高 `LIVE_SMALL_H=400` 的灰度图（与 `_gray_small` 目标一致，不重复降质），原图 px = 测量帧 px × `frame_scale`；③ 步长 `LIVE_STEPS=(1,2,3,5)` 自适应，中间掺坏帧会被**跨过去**而非污染总量。
  - 实时读数用 `measure_scroll_fast()`（整块 SAD、每 3 列取 1），逐块投票是百毫秒级跑不到 14fps。**两套算法要互相印证**：真机差 3~9%，自检 M5 断言 ≤15%。
  - **相同的帧 → 0 是对的，不是「测不出」**；「测不出」只留给互不相同又对不上的帧（自检 M3b / M3c 分开断言）。
  - 首帧延迟实测 **2.7s**（起流 + ffmpeg 缓冲），其中约 2s 是同步 `screencap` 取尺寸 —— 主画布已有帧时直接复用可省掉。窗口必须写明「首次出画面约 2~5 秒」，否则用户以为卡死。
- **「顶行贴红线」对齐的四条实测结论（2026-09-21，用户要求「滑动后下一批 6 张地图上排 3 张顶部精准贴红线」）**：
  1. **对齐锚点是行间亮缝，不是封面边缘**：行与行之间约 12px（视图）的亮缝在**三列上同时**「亮+平」（`detect_row_bounds`：横梯度中位数 <3.5 且亮占比 >85%，取三列 max/min），封面内容边缘做不到三列同齐。视口内第一张**完整**卡顶与 `first_row_y` 之差即 `drift`（纯计算拆在 `grid_drift()`，自检 N 段覆盖基准图/用户截图/合成滚动 16 档）。⚠ **2026-09-22 订正**：`spacing_ok`（缝隙间距核对行距）**不再作为「不符就停」的闸门** —— 缝距不符有两种成因：(a) 停在了非大厅页面（QQ 聊天列表，拦下是对的）；(b) **缝落在封面内部的浅色平坦区**（真机实测，卡片本身在大厅页，缝 `(300,325)` 落在封面天空/云雾上）。旧行为一律停会让 (b) 永久无法收敛，现改为**记录「缝可能落在封面浅色平坦区」并继续补滚**，由终局复测决定结果。
  2. **「顶部滑出屏幕却报已对齐」的真根因是「假缝」（2026-09-22，用户实测纠错）**：用户反馈「有时候滑动到红线识别也不准，地图顶部都滑上去超出屏幕了，还报顶行已对齐红线」。逐像素剖面证实**不是首行滑出**：真机 2400×1080（`shot_20260922_140417_001`）视口上沿之上是「**页面背景空档**（y=192..208，mean≈190 flat≈2.0）+ **3px 暗色分隔线**（y=209..211，mean=85 flat=0.0，即「全部」筛选行与卡片列表的分界）+ **又一截背景空档**（y=212..219，8px）」；亮缝检测只看「亮+平」不看色调，把这三段**合并成一个 11px 假缝** `gaps[0]=(210,220)`，而 `g1+1=221` **恰好等于真实卡顶**（y=220 flat 跳 58、y=221+ flat≈117）→ 算出 `drift=+11`（整行偏下），用户观感却是「明明没对齐却报已对齐」。同批 `shot_20260922_141831_002` 的缝 `(300,325)` 更是落在**首行卡片封面内部**（放大 `onecard_141831.png` 见封面/标题/标签/下载按钮全部完整可见）。→ 判据：`g0 <= y0+2` 判 `top_in_gap`（首行卡顶 = `g1+1`）；`(g0-y0) >= cover_h-tol` 判 `aligned`（首行卡顶 = 红线）；否则 `cut`（`g1+1` 已是下一行卡顶）。
  3. **⚠「首行已整行滑出（`scrolled_past`）+ 回退一行距反推首行卡顶」是被证伪的错误方向，已整体删除（2026-09-22 自我纠错，重要）**：按用户「顶部都滑上去超出屏幕」的字面描述，我一度新增 `scrolled_past` 状态与 `implied_top = g1+1-R` 反推、允许 `drift` 为负并触发反向回滚。**三重证据全部否证**：① 合成帧回归 S=157 档反推出 `drift=-157`，而正解是 `+157`（修前 16 档中 S=157..250 多档 FAIL）；② 141831 帧放大目视首行**完整可见**，反推却给负值；③ 全量 43 帧扫描，修前 4 个负 drift **全部是误判**。物理依据：视口上沿之上是页面背景/筛选行，不存在「还能反推出上一行」的结构；首行真滑出时信息不足以唯一确定偏移。→ **该状态、反推、`align_to_grid` 的 `if drift < -tol:` 反向回滚分支全部删除；`drift` 恒 ≥ 0**。原则同热度/评分的「宁可留空不写假值」：**宁可如实报「有偏差」也不给假值**。
  4. **cut 状态补滚过冲会「追行界死循环」**：cut 时检测器指向**下一行**的行界，补滚过冲哪怕 30px 就越过那条例行界，目标立刻跳到再下一行（真机实测 156→333→329→357）。对策：越界量 `s_past = 行距 - drift` ≤ max(80, 25%行距) 时**反向滚回当前行**（新增 `Adb.swipe_down()`，`precise_scroll` 加 `direction` 参数）。⚠ 该保护仍保留（它拦的是「正向补滚过冲」，与第 3 条被删除的「负 drift 反向回滚」是两回事）。
  5. **位移测量必须带方向**：`measure_scroll` / `measure_scroll_total` / `measure_scroll_fast` 都有 `direction` 参数，回滚返回**负值**；不做双向搜索（候选集翻倍会放大行距周期别名），方向由调用方给。`precise_scroll` 里回滚进度取绝对值入账。⚠ 改这段时 `tpl`~`while` 的**缩进必须留在 `for x` 内层循环里**——错一层缩进 = 每个块行只投一票，周期别名簇抢票，自检 I 段立刻 FAIL（2026-09-21 自踩，靠与备份 diff 定位）。
  6. **小位移补滚会撞触控 slop + 增益要按方向隔离**：真机 21~31px 手指只滚 3px，学习增益跌到 0.1 会反推出 370px+ 的巨型手指位移（fling 几百 px）。对策：手指位移夹到 `3×缺口+30px`；回滚增益只在本次调用内学习、不写回 `self.swipe_gain`；对齐补滚用慢速（≥1200ms）压制 fling。容差 = max(5, 2%行距) ≈ 8px@1080；终局 ±20px 内可能要多点一次（工具如实报「未收敛」），这是 `input swipe` 执行器的物理极限。真机端到端（扰动→闭环→复测）五次：357→14、161→0、162→18、18→0、161→0。工具文案已统一为「**偏差 >0 表示整行仍偏在红线下方，继续点「对齐」可再收敛一轮**」，避免用户按「滑出屏幕」方向理解。

- **热度/评分是「彩色小字压在封面/亮条上」，单配方读法必错（2026-09-22 双通路取证：12 张卡 × 6 配方 × 4 档 ≈ 600 次 OCR）**：
  - **三类实测失败**：① **前导数字丢失** —— 真机 `116万` 读成 `16万`/`1万`（值差 10 倍）、`101万` 读成 `0万`，**静默错值，最危险**；② **尾部粘连** —— `73.3万`→`73.3万福`、`21.1万`→`21.1万2`，读进来的是封面杂字；③ **亮条淡字整块丢** —— 基准图 `111万` 原样读只剩 `万`。
  - **有效配方三维度**（`read_heat`）：**原样**（基准图淡字最好）／**颜色增强灰** `color_gray`（灰度 = `clip((R−B)×2.2)`；真机红/珊瑚彩字显著提对比，但基准图这种被缩小的旧截图上更差 → 只能当**投票成员**）／**跳火苗框**（左边界 5.6→18.0 视图，避免火苗被读成前导数字）。**二值掩膜禁用**：会吃掉细笔画与小数点（`4.3`→`43`、`73.3万`→`733万`，反而造假值）。
  - **左边界只能右移，绝不能左扩**：加宽到 `0..62` 会让火苗被读成前导数字（`13.1万`→`0113.1万`、`202万`→`2202万`）。
  - **判定规则**（`decide_readings`，纯函数，自检 O2）：① 只有一个有效值 → 采纳；② 多个 → **数字位数最多**的（OCR 丢字远比凭空多字常见），位数打平 → 票数多者，再打平 → **弃权**；③ 全无效 → `sharp` + 跳火苗框复核（要求 ≥3/4 档一致）；④ 仍无 → 留空。配套 `heat_value()` 过滤假值：**无单位或数字以 0 开头**（`0万`、`0113.1万`）一律判无效 —— 宁可留空，不写假数值。
  - ⚠ **多配方读法别复用 `LOBBY["fields"]` 的字段框高度**（-2.2..21.7）：那是「窄框读法」的最小可用高度，用在多配方上会把彩字上沿切掉，实测读数直接退化（真机 `116万` 又变回 `16万`）。多配方统一用**信息带高度 -7..32.5 视图**。
  - **效果**：真机 2400×1080 **热度 6/6、评分 6/6**；基准图 1920×864 **热度 6/6、评分 4/6 + 2 个诚实留空**（那两张卡肉眼也难辨）。修复前：真机热度 4/6（含一个 10 倍错值）、基准图评分 3/6。
- **评分兜底只能「多左边界」，不能「跟着星标右缘自适应」（2026-09-22 量化 + 否决记录）**：顶部信息带是流式排版，星标与评分数字的 x 随热度文本宽度浮动（见第 4 节），固定左边界 71 在部分卡上会切进星标右尾 → 文本污染（`74.3`/`co4.5`）或读空。主读失败时用 `read_score_retry()`：左边界 74/78 视图 × `sharp`/颜色灰 × 4/6/8 档，多数票 ≥2 才采纳（能把基准图 r1c2 从 `75`（无小数点→None）救回 `4.5`）。**被否决的方案**：跟着**星标右缘自适应** —— 星标与数字紧贴时右缘算不准，实测会把数字首位切掉（`3.6`→`36`、`4.3`→`3`），比固定框更差。兜底的裁切失败形态是「丢小数点」（`36`/`43`），`parse_score` 直接返回 None —— 所以它**只会补值、几乎不会造假值**，这也是敢在失败时才启用它的原因。
  - 展示列（表格/导出）只放**解析命中的真值串**：`74.3`→`4.3`、`co4.5`→`4.5`、`73.3万福`→`73.3万`；原始 OCR 串留在隐藏列 `_raw_热度` / `_raw_评分` 供复核（导出时自动丢弃）。
- **给位移测量造合成样张必须有纵向结构（2026-09-21 自踩）**：纯色 / 近纯色的图在任何位移下残差都是 0，`measure_scroll()` 直接返回 0 —— 用它测「等滚停」会得到「2 次截屏就停稳」的**假通过**（全绿但没测到任何东西）。样张要画成多条颜色+文字都不同的卡带，并在用例里**先断言「50px 位移量得出 50」**，再跑真正的等停用例。
- **界面各区域要能滚动、能调大小（2026-09-20 晚）**：右栏内容在横屏/小屏下超出屏幕、底部按钮点不到。定式：外层 `ttk.PanedWindow(VERTICAL)`（主体/日志，拖条改高度）+ 内层 `HORIZONTAL`（画布/右栏）；右栏 `Canvas + 双向 Scrollbar + create_window`，窗口宽度在 `<Configure>` 里 `itemconfigure(width=e.width)` 跟随；日志补 Scrollbar；滚轮 `bind_all` **必须先给滚动容器本身开后门**（否则右栏大部分面积就是那个 Canvas，被「自带滚动控件放行」规则挡掉 → 「滚轮在右栏没反应」）。⚠ **先建外层再建内层**，写反会 `UnboundLocalError`。
- **换分辨率后旧几何可能仍然「看起来对」**：1920×864 下侥幸成立的框，按比例换算到 2400×1080 后可能正好把相邻图形圈进来（评分/星标即此例）。**换机后第一件事是跑 `test_regress.py` 看评分列**，不要凭 1920 上的结论外推。
- **区间校验只能拦「粗错」**：`36`、`736` 能拦；但 `A2 → 2` 落在 (0,10) 之内，拦不住 —— 该假值已由 `parse_score()` 在解析层消掉（无小数点直接返回 `None`）。所以评分数值列仍不可全信，只作参考。
- **RapidOCR 跨进程结果抖动**：同一张固定裁切图，不同次运行可能给出不同结果（淡字尤甚）。任何「单次读取当结论」的写法都不可靠，数值字段必须多档投票。
- **黑屏**：FLAG_SECURE 界面 `screencap` 得到黑图，不是 bug；改拍照导入。
- **自选模式曾静默失效（2026-09-18 修复）**：`field_rect` 早期版本无条件优先取 `LOBBY` 偏移，导致自选模式下用户亲手拖的框**完全不生效**却不报错；`FIELD_PAGE_UNAVAILABLE`（评论数）也曾被无差别应用到自选模式。两者均已按布局模式分支修正。
- **自检脚本会随主程序改接口而断裂**：`FIELDS` 扩容后 `test_pipeline.py` 抛 `KeyError: '标签'`；`recognize_frame` 改为返回三元组后，自检仍按单值解包而抛 `AttributeError`。三处均已修。**改主程序公开接口后必须重跑两个验证入口。**
- **自检跑完不退出**：C 段创建过 Tk 与 onnxruntime 会话后，即使走到 `root.destroy()`，仍有非守护的本地线程吊住解释器 —— 实测打印 `done` 之后进程 5~6 分钟不结束，只能手工 kill，容易被误判成「还在跑 OCR」。已在自检末尾用 `os._exit(0)` 硬退出（结果文件早已落盘，硬退出不丢数据）。
- **中文字体路径**：自检脚本用 `msyh.ttc` 合成样张，缺字体会跳过 OCR 用例。
- **删除临时文件**：本机 safe-delete 钩子对 `D:\知识库\...` 下 `Remove-Item` 报 `trash-failed`，但文件实际已删；清理后必须用 `Get-ChildItem` 复核，不能只看报错。
- **步长错位（自选模式）**：卡片步长不准会把上一张的数值框进下一张，表现为「评分列出现热度数值」——先缩小框、再调步长。
