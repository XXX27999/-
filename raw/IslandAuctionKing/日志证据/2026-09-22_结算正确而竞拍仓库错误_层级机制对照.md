# 为什么结算界面图片在上层，而竞拍仓库界面图片在格子下面

- 日期：2026-09-22
- 结论等级：**实测确认**（代码对照 + 双客户端 PIE 活体读数）
- 相关文件：
  - `Script/Function/AuctionSettlementUIService.lua`（结算，**正确**）
  - `Script/Function/AuctionWarehouseCellService.lua`（竞拍仓库，**出错**）
  - `Script/Function/AuctionTestUIService.lua`（竞拍仓库刷新入口，遮挡色写入处）
  - `Script/Function/AuctionWarehouseImageMaterialService.lua`（遮挡色来源）

---

## 一、一句话回答

**两边用的都是同一个单格控件 `CollectibleCodexItemUI_C`，但「怎么用」完全相反：**

- **结算**：单格只当**底层背景格**用，然后**另建一个控件实例**承载藏品图片，作为**独立的兄弟控件**追加到画布末尾。
  → 藏品图天生就是一个「排在最末尾的兄弟」，永远画在格子之上，**不依赖任何 z 值**。
- **竞拍仓库**：把藏品图片放在**蓝图预先摆好的 `CollectibleImage01..32`** 里，靠运行时搬迁 + 设 z。
  而这两条路在本引擎**都不控制绘制顺序**，且单格自身的按钮背景是**不透明**的。

**所以结算「看起来层级对」，不是因为它层叠做得好，而是因为它压根没用同一套机制。**

## 二、代码级对照（逐条证据）

### 2.1 结算：图片是「新建的独立兄弟控件」

`AuctionSettlementUIService.lua:1093-1118`

```lua
local visualWidth  = (maxX - minX) * layout.CellStep + layout.CellSize
local visualHeight = (maxY - minY) * layout.CellStep + layout.CellSize
local x = layout.OriginX + minX * layout.CellStep
local y = layout.OriginY + minY * layout.CellStep
local cellWidgetClass = UGCObjectUtility.LoadClass("...CollectibleCodexItemUI.CollectibleCodexItemUI_C")

local addOK, addSlot = AddChildToCanvasSafe(layout.ParentCanvas, overlayWidget) -- ← 追加到父画布末尾
...
if not addOK or not ConfigureCanvasSlot(canvasSlot, x, y, visualWidth, visualHeight, 40)
   or not ConfigureImageOnlyWidget(overlayWidget, visualWidth, visualHeight) then
```

关键三点：
1. `NewWidgetObjectBP` **新实例** → 名字不在蓝图里，是全新的控件；
2. `AddChildToCanvasSafe` 把它**追加**到 `layout.ParentCanvas` 子列表末尾；
3. `ConfigureImageOnlyWidget` 把该实例**除了图片以外的所有东西都折叠/透明**（见 2.3）。

因为它是**最后被追加的兄弟**，而本引擎绘制顺序 = 子控件插入顺序（后者在上），所以它必然在最上层。

### 2.2 结算的背景格：按钮底色被显式归零

if cellWidget.ItemButton ~= nil then

## 三、竞拍仓库为什么反过来

### 3.1 图片走的是「蓝图预置控件 + 运行时搬迁」

`AuctionWarehouseCellService.lua:566-588`（`EnsureOverlays`）

```lua
for displaySlot = 1, scanLimit do
    local names = {string.format("CollectibleImage%02d", displaySlot),
                   string.format("CollectibleButton%02d", displaySlot)}
    for _, widgetName in ipairs(names) do
        local child = widget[widgetName]          -- ← 蓝图里预先摆好的控件
        ...
        contentCanvas:AddChildToCanvas(child)     -- ← 搬进内容画布
        child.Slot:SetZOrder(layout.overlayZOrder)
```

**关键差异**：`AddChildToCanvas` 只负责「把它挂进这个父容器」，
**对「已经在同一个父容器里」的控件不会改变它在子列表中的相对位置**。
所以这次搬迁**不会**把图片挪到格子之后 → 顺序仍然是「图片在前、格子在后」→ 格子画在上面。

### 3.2 背景格按钮底色是**不透明**的（真正遮挡源）

三层来源叠加：

**(a) 蓝图设计态默认**：`ItemButton` 的 `BackgroundColor` 本身就是不透明。
2026-09-22 活体实测（`doluastring` 探针，客户端 528800）：

```
CELL=ud_object[CollectibleCodexItemUI_C ... AuctionTestUI_C_0.CollectibleCodexItemUI_C_0]
BTN =ud_object[Button ... AuctionTestUI_C_0.CollectibleCodexItemUI_C_0.WidgetTree_1.ItemButton]
A=1.0 R=1.0        ← 完全不透明，且是白色
```

**(b) 上游刷新每次覆写**：`AuctionTestUIService.lua:862, 906`

```lua
local gridBaseColor = AuctionWarehouseImageMaterialService.GetGridBaseColor(widget, EMPTY_COLOR)
...
button:SetBackgroundColor(gridBaseColor)
```

`AuctionWarehouseImageMaterialService.lua:8, 396-409`：

```lua
local GRID_TEXTURE_TINT_COLOR = {R = 1.00, G = 1.00, B = 1.00, A = 1.00}  -- ← A=1.0
...
local usesGridTexture = widget ~= nil and widget.AuctionGridTextureApplied == true
local resultColor = usesGridTexture and GRID_TEXTURE_TINT_COLOR or fallbackColor
```

纹理已应用 → 乘色 = **纯白不透明**。

**(c) 回退分支也是 92% 不透明**：`AuctionTestUIService.lua:71`

```lua
local EMPTY_COLOR = {R = 0.03, G = 0.04, B = 0.06, A = 0.92}
```

> 即：**无论走哪条分支，背景格按钮都是不透明/近不透明的填充。**
> 这是结算里被显式写为 `A=0` 的那一层，在竞拍仓库里从未被清零。

### 3.3 时序：为什么之前把 `A=0` 写进 `EnsureCells` 也没用

```
Initialize / RefreshWarehouse
        │
        ├─ EnsureCells(widget)            ← 建房格；我在这里写了 A=0
        │      └─ EnsureOverlayOrderAfterCells  ← 顺序断言
        │
        └─ for cellIndex=1,84 do          ← 之后才执行
                 button:SetBackgroundColor(gridBaseColor)   ← 又把 A 覆写成 1.0 / 0.92 ★
```

**`EnsureCells` 的 `A=0` 被紧随其后的 `RefreshWarehouse` 覆盖。**
这正是「日志说改了、画面没变」的原因。

## 四、四次受控实验（第六轮，用于交叉验证）

| # | 操作 | 结果 | 推论 |
|---|---|---|---|
| ① | 基线 | 网格纯暗空格，无藏品图 | 复现问题 |
| ② | 84 格整体 `SetVisibility(Collapsed)` | **藏品图立即显现** | 遮挡源在格子自身 |
| ③ | 覆盖层 z 40 → 5（低于格子 10） | **仍被遮挡** | **z 不参与排序** |
| ④ | 84 格 `ItemButton` 背景 `A` → 0 | **整片暗方格整体消失** | 确证按钮背景即不透明遮挡层 |
| D | 覆盖层 `RemoveFromParent`+`AddChildToCanvas` | **仍被遮挡** | 搬迁不改变已同父控件的相对顺序 |

第七轮补充活体读数（用于确认顺序本身没问题）：

```
【AuctionWarehouseCellService+EnsureOverlayOrder】关键数据
  appliedCount=64 wrongCount=0 missingCount=0 childCount=148 lastCellIndex=83
```

`childCount=148 = 84 格(idx 0..83) + 64 覆盖层(idx 84..147)`，
`lastCellIndex=83` 且 `wrongCount=0` → **覆盖层确实已排在所有格子之后**。
但画面依旧被盖 → **只可能是「同父顺序对了，但格子的不透明填充画在了更上层」。**

## 五、修复方向（两处，缺一不可）

| # | 位置 | 动作 |
|---|---|---|
| **1** | `AuctionTestUIService.RefreshWarehouse:906` | 背景格按钮的乘色**不能是不透明**。改为 `{R=0,G=0,B=0,A=0}`；若必须保留底色，只能靠**已经透明**的独立底板控件，而不是按钮自身填充 |
| **2** | `AuctionWarehouseImageMaterialService.GetGridBaseColor` | `GRID_TEXTURE_TINT_COLOR` 的 `A` 由 `1.00` 改为 `0`（或直接不写按钮底色，改由图片格控件承载纹理） |
| 3 | `AuctionWarehouseCellService.EnsureCells` | 已有的 `A=0` 写法**必须挪到 `RefreshWarehouse` 之后**，否则必被覆写（当前无效） |
| 4 | 顺序断言 | 保留第七轮新增的「按子控件序号断言」（`EnsureOverlayOrder`），它已证明能正确报告顺序 |

**只做 1+2+3 即可让藏品图浮于格子上方**——即结算里那条已经跑通的路径：
`背景格 A=0` + `图片在末尾`。

## 六、方法学

1. **别问「哪边代码更好」，要问「两边差在哪一行」。**
   同一单格控件、同一引擎，结算对、仓库错 → 差异一定在「谁设了什么值」上，逐行对照即可定位。
2. **`SetZOrder` 在本引擎不驱动绘制顺序**（实验③）。任何「调 z 抬层」的思路都要先证伪。
3. **`AddChildToCanvas` 对已在同父的控件不改变顺序**（实验D）。
   要让控件真正排到末尾，必须先 `RemoveFromParent` 再 `AddChildToCanvas`（当前 `RaiseOverlays` 已正确实现）。
4. **改一个值要确认「谁是最后一个写它的」**（3.3 时序）。
   写入点在上游刷新之前 = 白改。
5. **日志全绿 ≠ 画面正确**：`appliedCount=64 / wrongCount=0` 只证明顺序对，
   不能证明「没被不透明层盖住」——判据必须同时覆盖「顺序」与「不透明度」两个维度。
