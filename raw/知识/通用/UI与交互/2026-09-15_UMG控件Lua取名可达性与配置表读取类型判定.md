## 一、三条结论（可直接照用）

1. **Lua 侧 `widget["控件名"]` 只在控件 `bIsVariable=True` 时可达。**
   UMG 设计器里未勾选 “Is Variable” 的控件不进入生成类属性表，Lua 用 `widget["UIText01"]` 取到的是 `nil`；此时唯一可用路径是 `widget:GetWidgetFromName("UIText01")`。
   - 实测：本资产 86 控件中，31 个按钮 + `PreviewImage` 为 True（全部可达），38 个 TextBlock **全为 False**（全部取不到）→ 三个列表的按钮文案运行时全空。
   - 推论边界：`widget[name]` 取不到 ≠ 控件不存在。控件仍在控件树内（契约名齐全），只是没有暴露成蓝图变量。

2. **`UGCGameSystem.GetTableData(path)` 返回的是 userdata 包装，不能用 `type(x)=="table"` 判定。**
   - 实测：`luaType=userdata`，`tostring` 为 `TableStruct: 000000023658DE08`；行对象 `t["格子"]` 的 `tostring` 为 `TableDataStruct: 00000001218CDF88`。
   - 但它**可正常 `pairs()` 迭起**：`rowCount=15`、`firstRow=白品质`、`t["格子"].MaterialSource=Texture2D /IslandAuctionKing/Asset/TuPian/ImageMaterial/a7.a7`。
   - 正确判定：只判 `readOK and x ~= nil`（与 `AuctionWarehouseImageMaterialService` 一致）；对本表与行都加 `type()=="table"` 判定会把数据静默吞掉（返回 0 行、无报错、只有业务侧日志显示“列表为空”）。

3. **槽位数量由配置决定，未使用的槽位不会自动隐藏。**
   `UI.Dress.UISlotCount/RegionSlotCount/MaterialSlotCount` = 4/10/16，而实际数据是 3 个界面 / 3~8 个区域 / 15 行材质 → 运行时多出的空槽依然占位显示（区域列出现 7 个空框）。需在刷新逻辑里按实际条数显式 `SetVisibility`。

## 二、证据摘录

- 控件回读：`TOTAL=86`；`BTN_VAR=31`（UIButton01-04 / RegionButton01-10 / MaterialButton01-16 / CloseButton）；`TEXT_VAR=0`；`TEXT_NOVAR=38`；`IMG_VAR=1`（PreviewImage）。
- 运行时绑定：`BindEvents` 逐条输出“已绑定一级/二级/材质按钮 index=N”，无任何“缺失”分支 → 31 个按钮按名字全部可达。
- 运行时取名：`w["UIText01"] = nil`（MISSING）；`StatusText` 走 `GetWidgetFromName` 才 `found=true`。
- 表读取：`pairsOK=true rowCount=15`（行数正确但被 `type()` 判定拦下）。
- 截图：`pie_dress_client.png`（1280×720 绘制区）可见列表头为金色、按钮为深色卡片样式、选中项着色正确，但三列文案全空。

## 三、正确写法

Lua 取名（兼容未暴露控件）：

```lua
-- 控件按名字取：优先直取，失败再走 GetWidgetFromName（未标记 Is Variable 的控件走这条）
local function ResolveNamedWidget(widget, name)
    if widget[name] ~= nil then
        return widget[name]
    end
    local ok, resolved = pcall(function() return widget:GetWidgetFromName(name) end)
    if ok then
        widget[name] = resolved
    end
    return ok and resolved or nil
end
```

或者更省事：在 UMG 资产侧把需要 Lua 写文案的文本控件勾上 Is Variable（MCP 侧即 `w.bIsVariable = True` 后 `compile_blueprint` + `save_package`），既有 Lua 无需改动。

表读取：

```lua
local readOK, tableOrError = pcall(UGCGameSystem.GetTableData, tablePath)
-- 返回值是 userdata 包装（TableStruct），只判非空，不要判 type()=="table"
if not readOK or tableOrError == nil then
    ugcprint("【模块+函数】错误 表格读取失败 runtimeType=" .. tostring(type(tableOrError)) .. " error=" .. tostring(tableOrError))
    return
end
for rowKey, rowData in pairs(tableOrError) do
    if rowData ~= nil then -- 行对象同样是 userdata
        local texture = rowData.MaterialSource
    end
end
```

未使用槽位折叠（纯展示层）：

```lua
local visibility = index <= usedCount and ESlateVisibility.Visible or ESlateVisibility.Collapsed
pcall(function() button:SetVisibility(visibility) end)
```

## 五、reloadlua 生效边界（实测，机制未查证）

- 实测：修改 `Script/Function/AuctionDressUIService.lua`（含改变错误日志文案）后调用 `reloadlua`，客户端日志显示已 `AppendLuaFileToHotReloadMessage` + `Start With For Client Hotreload`，但随后同一函数仍输出**旧版日志文案与旧行为** → 判定该模块的 Lua 修改**未生效**。

## 六、未结问题：按钮内文案（Button.Content）不绘制

同一资产内出现干净的二分现象：

| 文本控件 | 父节点 | 是否绘制 |
| --- | --- | --- |
| TitleText / UISectionTitle / RegionSectionTitle / StyleSectionTitle / PreviewCaptionText / PreviewHintText / StatusText / CloseLabel | `DressPanel`（CanvasPanelSlot） | 绘制正常 |
| UIText01-04 / RegionText01-10 / MaterialText01-16（30 个） | 各自 Button 的 Content（ButtonSlot） | **完全不绘制** |

已用运行时取值为该 30 个文案逐项排除（全部与「能正常绘制」的控件一致或无异常）：

- 文案内容：运行时 `GetText()` 返回实际值（如 `主界面`），强制 `SetText("ABC123")` 后仍不显示 → 排除「无文案」与「缺中文字形」。
- 颜色：`ColorAndOpacity.SpecifiedColor = (0.929,0.929,0.937,1)`、`ColorUseRule=0(UseColor_Specified)` → 近白不透明，深色按钮上应当清晰可见。
- 字号/字面：`Font.Size=22`、`TypefaceFontName=Bold`；`FontObject=/Engine/EngineFonts/Roboto.Roboto` 与正常绘制的表头**完全相同** → 排除字体家族/字体资产差异。
- 可见性：设计态与运行时 `Visibility=0(Visible)`；`RenderOpacity=1.0`；`Opacity=1.0`。
- 变换：`RenderTransform` 为恒等（`Scale=(1,1)`、`Translation=(0,0)`、`Angle=0`）。
- 排版：`ButtonSlot` 为 `HAlign=2(居中)/VAlign=2(居中)`、`Padding=(4,2,4,2)`；按钮 `NormalPadding=(2,2,2,2)`、`PressedPadding=(2,3,2,1)`。
- 按钮画刷：`Normal/Hovered/Pressed` 均为 `DrawAs=1(Box)`、`ResourceObject=None`、`Margin=0.25`、`ImageSize=32×32`（`Disabled` 为 `ImageSize=0`、`Margin=0`）。
- 层级：三列 `Z=2`，卡片底 `NavCard/PreviewCard/StyleCard` 为 `Z=0`、`PreviewWell` 与表头为 `Z=1` → 列在底图之上，无遮挡。
- 结构：运行时 `UIButton01:GetContent()` 返回的正是 `WidgetTree_2.UIText01`，`content==UIText01=true` → 文案确实挂在按钮内容槽上，未脱离控件树。
- 归因：该现象在 `bIsVariable` 修正**之前**已存在（当时该文案的 `Text` 为空，因此只表现为「空框」，无法显示）；不属本轮变量标记引入的回归。

**判据**：`GetDesiredSize()` 在本引擎不可用于定位（本资产 86 控件在设计态与运行时**全部**返回 `(0,0)`，含肉眼可见的 `StatusText` 与 `UIButton01`）→ 不能据其判定尺寸为零。

**下一步（未完成）**：需要用 UMG 设计器目视该资产三列按钮（设计态是否同样不绘制），确认「按钮内容区被分配为零尺寸」还是设计态本身如此；若确认，则文案需从 `Button.Content` 改为按钮之上的兄弟节点（Overlay/CanvasPanel + 独立 TextBlock）。

## 八、GetName 属性查找会抛异常，pcall(obj.Method, obj) 拦不住（2026-09-21 项目实测追加）

- **实测**（IslandAuctionKing `AuctionWarehouseCellService.ApplyCellChrome`，两轮 PIE 复现）：对运行时创建的
  `CanvasPanel` / `Border` / `Image` 取 `obj.GetName` 属性会抛 `LuaExtend_GetProp ... property not exist`，
  且同一控件**时有时无**（18:02 一轮每格必抛、18:03 一轮同代码未抛，疑为属性查找竞态）。
- **关键坑**：`pcall(child.GetName, child)` 的**索引动作发生在 pcall 之外**——`child.GetName` 一抛就直接外逃，
  pcall 根本没开始执行；必须把整个取值放进闭包：`pcall(function() return child:GetName() end)`。
- **后果量级**：该异常让 `EnsureCells` 每格创建中断 → 84 个动态格全部失败 → 业务回退到遗留固定格并遮挡滚动内容
  （「藏品图被格子遮挡」的表象根因，详见 IslandAuctionKing 项目 Raw 2026-09-21 同名页）。
- **规范**：凡对 UMG 控件做属性/方法访问的防御性调用，一律写 `pcall(function() return obj:X(...) end)`，
  禁止 `pcall(obj.X, obj)` 形态。

## 九、`GetName`/`GetClass`/`GetChildrenCount`/`GetChildAt` 在本引擎子控件上整体不可用；`pcall` 挡不住异常日志（2026-09-22 项目实测追加）

- **实测**（IslandAuctionKing `AuctionWarehouseCellService.ApplyCellChrome` 的递归兜底分支，第二轮 PIE）：
  对运行时创建的 `CollectibleCodexItemUI_C` 子控件（`CanvasPanel` / `Border` / `Image` / `TextBlock`）分别取
  `GetName` / `GetClass` / `GetChildrenCount`，**全部**报 `LuaExtend_GetProp ... property not exist`：

  ```text
  Object [CanvasPanel ...ItemContent]   PropName [GetName]: property not exist
  Object [Border    ...CardBackground]  PropName [GetName]/[GetClass]: property not exist
  Object [Image     ...ItemImage]       PropName [GetName]/[GetClass]/[GetChildrenCount]: property not exist
  ```

  直接后果：以「控件名 / 控件类」为判据的折叠逻辑**恒不成立**，实测 `控件树清单=(),(),()...`、`collapsedDecorations=0`，
  整段兜底沦为死代码。
- **比第八节更要紧的一点**：`pcall` 只能阻止错误外抛，**不能阻止引擎写日志** —— 每次失败仍产生一整段
  `[LuaException] LuaExtend_GetProp ...` + `stack traceback`。实测 84 格 × 每格约 300 行，
  `EnsureCells` 从 10:28:44 跑到 10:30:00，**开局卡约 76 秒**，LuaLog 单会话 9.6 MB + 9.9 MB。
  →「包一层 pcall 就安全」是错的；**性能敏感路径上必须从源头避免探测不存在的成员**。
- **正确做法**：
  1. 要「按名取控件」→ 用 `UUserWidget.GetWidgetFromName`（实测可用，每格 9/9 命中，且覆盖整棵控件树）。
  2. 要「遍历子控件」→ 只在**已知类型的容器**上调 `GetChildrenCount`/`GetChildAt`，不要对未知子控件试探。
  3. 折叠/隐藏改为**名称清单驱动**（枚举控件名 → `GetWidgetFromName` → `SetVisibility`），不做类名判定。
  4. 要「判断控件是否存在」→ 直接判 `widget.名字 ~= nil`（bIsVariable）或 `GetWidgetFromName(...) ~= nil`，不要拿 `GetName` 反推。
- **取证位置**：客户端 LuaLog `Saved\Logs\<项目名>\Clientlog\LuaLog\<会话>_1/_2.log`；
  **会话进行中该文件为 0 B，PIE 停止后才落盘**（实时只有 DS 侧 `DSlog\FullLog\*_realtime.log` 在写）。
