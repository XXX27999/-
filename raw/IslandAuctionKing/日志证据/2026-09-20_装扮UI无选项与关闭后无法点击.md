## 1. 根因一：残留调用 `ApplyPreviewMaterial`

### 日志证据

```
16:04:35:660 【AuctionDressUIService+Refresh】错误 刷新异常
  error=Script/Function/AuctionDressUIService.lua:190: attempt to call a nil value (global 'ApplyPreviewMaterial')
16:04:37:104 LogTagLog: Error: [LuaException] LuaPCallFailed
  CallLuaUFunction Failed: UFuncSig=[OnButtonClickedEvent__DelegateSignature]
  info=Script/Function/AuctionDressUIService.lua:190: attempt to call a nil value (global 'ApplyPreviewMaterial')
```

同一个错误在 16:04:35 / 16:04:38 / 16:04:41 各出现一次，`Refresh 出口 success=false` 紧跟其后。

### 为什么表现为「没有可选项」

`ApplyPreviewMaterial` 随材质列表一起被删除（旧实现见提交 `028ce94` 的
`Script/Function/AuctionDressUIService.lua:266`，本体就是 `previewImage:SetBrushFromTexture(texture, false)`），
但 `ApplyStyleThemeToFolder` 第 190 行的调用点**没跟着删**。

`Refresh` 的执行顺序是：取分类 → 取主题列表 → **`ApplyStyleThemeToFolder`（190 行在此抛异常）** → 刷右侧主题按钮 → 状态栏 → `PersistSelection`。
`pcall` 把异常吞掉只打一行日志，**抛异常点之后的所有代码都不执行**：

- 右侧 `MaterialButton%02d` 的文案与 `MarkSelected` 没跑 → 按钮保持初始态（空白/不可见）
- `KeepSlots("Material", ...)` 没跑 → 槽位没有按主题数展开
- 状态栏没更新
- `PersistSelection` 没跑

→ 用户看到的就是「右侧没有可选项、状态栏没内容、像是没读表」。

### 为什么只在 Hub 分类触发

`ApplyStyleThemeToFolder` 走到 190 行的前提是「预览素材取到了」。

- `Hub` 的 `Preview=ZJMBackground`，`LoadSameNameTexture` 成功 → 走到 190 → 崩
- `Auctioninterface` / `Settlement` / `Codex` 的 `Preview` 取不到（`Dress.SameName.BaseFolder.<UiKey>` 未配置，报
  `LoadSameNameTexture 错误 目录或素材名为空，加载中止`）→ 186 行提前 `return false` → **不崩**，`Refresh 出口 success=true`

所以日志里出现「切到竞拍/结算/图鉴分类 Refresh 成功、切回主界面就失败」的交替现象，与本推断完全一致。

### 修复（2 处）

1. **190 行**：内联 `pcall(SetBrushFromTexture(texture, false))`，两参失败再试单参（UBorder 形式）；预览控件缺失单独判空返回 false。
2. **Refresh 里调用点**：`ApplyStyleThemeToFolder` 改为 `pcall` 包裹，异常时 `styleApplyOK=false` 并打日志，**继续刷新列表**。
   —— 这一步是防御性的：预览属于展示细节，绝不该有能力让整个列表刷不出来。

## 2. 根因二：`FinishHide` 销毁方式不齐，装扮层留在视口吞点击

### 日志证据

```
16:04:49:487 【AuctionDressUIService+FinishHide】入口 widget=ud_object[AuctionDressUI_C ...]
16:04:49:490 【AuctionDressUIService+FinishHide】关键数据 destroyOK=true error=nil
```
此后到日志结束（16:05:06，约 17 秒）：
- `【AuctionHubUIService+Refresh】出口 success=true` **每帧都在**（主界面 Tick 完全正常，`matchButtonEnabled=true`）
- **没有任何一条按钮点击回调日志**（`OpenDress` / `OpenWarehouse` / `OpenShop` … 全 0 命中）

即：**Lua 侧活着，但鼠标点击一个都没进到回调里**。

### 与既有写法的差异（决定性）

`AuctionHubUIService.Hide`（1174-1195 行）销毁主界面是**两步**：

```lua
local hideOK,    hideError    = pcall(UGCWidgetManagerSystem.HideWidget,    widget) -- 先隐藏/移出视口
local destroyOK, destroyError = pcall(UGCWidgetManagerSystem.DestroyWidget, widget) -- 再销毁
if not hideOK then
    local removeOK, removeError = pcall(widget.RemoveFromParent, widget) -- 兜底
    hideOK = removeOK
end
```

装扮层的 `FinishHide` **只有 `DestroyWidget`，没有 `HideWidget`，也没有 `RemoveFromParent` 兜底**。

### 为什么 `destroyOK=true` 不能证明销毁成功

`destroyOK` 记的是 **`pcall` 的返回值**（是否抛出 Lua 异常），不是 `DestroyWidget` 的业务返回值。
这就是项目既有教训「**`pcall` 成功 ≠ 返回值可用**」的重演：只打 `destroyOK` 会把「调用成功但没生效」误判成「已销毁」。
装扮层 `AddToViewport` 的 zOrder = 502，根控件铺满屏幕且 `Visible`，留在视口最上层就会吃掉下面所有 UI 的命中测试。

### 修复

`FinishHide` 对齐 `AuctionHubUIService.Hide`：先 `Shutdown` → `HideWidget` → `DestroyWidget` → `HideWidget` 失败时 `RemoveFromParent` 兜底，
并分别记录 `hideOK/hideError/destroyOK/destroyError`。

## 6. 切换 TestTopic 主题后界面错乱 = 主题素材几何不匹配（同日追加）

### 现象

切到「山水」（TestTopic）后，主界面所有画刷都换成了蓝色系新素材（**机制链路本身通了**），但整体错乱变形：
顶栏蓝色横幅比例怪异、左下多出一大块面板、文字与底图相互压盖。

### 实测数据（MCP 逐张对比两套同名贴图的 Source.SizeX/SizeY）

| ZJM1 | 每日任务/帮助/保底金上方UI ×3 | 1118×113（9.9） | 294×47（6.3） | ✗ |
| ZJM3 | 玩家名称/服务器剩余时间 ×2 | 1920×1080（1.78） | 485×83（5.8） | ✗ 差异极大 |
| ZJM5 | 头像框 | 1254×1254（1.0） | 211×192（1.1） | 接近 |
| ZJM6 / ZJM7 | 帮助 / 每日任务 | 1254×1254（1.0） | 154×205 / 152×203（0.75） | ✗ 方形 vs 竖版 |
| ZJM8 | 金币 | 1024×1024 | 1024×1024 | ✓ 唯一完全一致 |

12 张里只有 `ZJM8` 长宽比一致；另注意**基目录侧本身也不全是"控件级切图"**（`ZJM3` 是 1920×1080 整图、
`ZJM5/6/7` 是同一张 1254×1254 方图），说明现版式当初就是靠"整图+透明通道"压出来的。

### 根因

同名画刷机制的既定生效范围就只有 `Brush.ResourceObject` 贴图，**不改控件矩形/锚点/拉伸方式**。
UMG Image 把贴图画进控件矩形，贴图长宽比与矩形不一致时会被拉伸变形；
而 `ZhuJieMian_TestTopic` 是**另一套设计稿的独立切图**（横竖构图与现版式完全不同），不是按当前 14 个控件的几何逐张出的换皮图。

→ **结论：代码无缺陷，是主题素材的几何/构图不满足「同名替换」的前提（逐控件同比例同构图）。**

### 修复方向（三选一）

1. **按现版式重切 TestTopic 素材**（推荐）：以当前主界面 14 个控件的矩形比例为模板做换皮，同名文件替换；
2. **机制上支持"主题自带布局"**：把每主题的控件矩形/锚点也进配置表——大改动，与「仅客户端展示层、不改布局」的既定范围冲突，需单独立项；
3. **快速验证法**：先只保留 `ZJM8`（比例一致）替换、其余回退基目录，确认界面无变形，即可证明结论并作为素材验收标准（逐控件长宽比一致）。

### 经验

「同名画刷换肤」对素材有一个隐含硬约束：**主题素材必须按同一版式逐控件同比例切图**。
做主题素材前先导出 14 个控件的几何（`hub_widget_tree.txt` 已有），按几何出图；验收先比长宽比，再看视觉。

### 追加：映射表会随设计态修改过期（服务器剩余时间案例，同日 17:3x）

**现象**：同一控件「服务器剩余时间」，PIE 里是中央一小段深灰条+四周透出橙黄背景，UI 编辑器里却是完整横条。

**实测链**：
1. 蓝图设计态（MCP 回读 Brush）：`服务器剩余时间 → ZJM1`（1118×113 全宽横条），`玩家名称 → ZJM3`；
2. 映射表：`Dress.SameName.Texture.Hub.ZJM3 = 玩家名称,服务器剩余时间`（当日早些时候由控件树导出）；
3. PIE 运行时按映射表把「服务器剩余时间」换成 ZJM3 —— 而 **ZJM3 是 1920×1080「整图+透明通道」素材**
   （导出 TGA 实看：只有画布中下部一小段横条图案，约 17% 宽，其余全透明）→ 整图压进 300×40 控件后
   只显示中央一小段、其余透明露出背景（橙黄跑道地面）。
4. 结论：**用户当天在编辑器里把该控件的图从 ZJM3 改挂为 ZJM1，映射表没跟着更新** → 运行时强改回 ZJM3。

**修复**（已执行并回读，改前全表备份 `Before_FixSrvTime\DressControlTable_backup.json`）：
- `Dress.SameName.Texture.Hub.ZJM3` → `玩家名称`
- `Dress.SameName.Texture.Hub.ZJM1` → `每日任务上方UI,帮助上方UI,保底金上方UI,服务器剩余时间`（TestTopic 的 ZJM1 为 294×47，比例与横条控件匹配）

**规律**：控件树导出的同名映射是**导出时刻的快照**。凡在 UI 编辑器里手工改过控件贴图，必须同步更新
`DressControlTable` 的 `Dress.SameName.Texture.*` 行，否则运行时会按旧映射把新图覆盖回去——
表现为「编辑器与 PIE 不一致」。映射对齐应作为换肤调图后的固定收尾步骤。

## 7. 追加：装扮 UI 无法正常运行（会话 `_dkck7pp6wxb8q9`，18:02 PIE）

### 现象

用户反馈「装扮 UI 无法正常运行」—— 装扮层能打开，但列表、主题按钮、状态栏全空，点什么都没反应。

### 根因：`ResolveNamedWidget` 漏写前向声明（一行，致命）

日志 7 次命中同一条：

```
[2026.09.20-18.02.39:518] 【AuctionDressUIService+Refresh】错误 刷新异常
  error=Script/Function/AuctionDressUIService.lua:76: attempt to call a nil value (global 'ResolveNamedWidget')
[2026.09.20-18.02.39:519] 【AuctionDressUIService+CreateAndShow】关键数据 viewportOK=true fadeOK=true error=true
```

链路：`ResolveDressWidget`（68 行）在 `widget[name]` 直取失败后回退调用 `ResolveNamedWidget`，
而后者是 **309 行的 `local function`**，定义在调用点之后又没有前向声明 → 调用点拿到的是**全局 nil**。
`Refresh` 一进去第一行就抛错（外层虽有 pcall 兜住不崩，但整段渲染逻辑全部跳过）→
一级列表 / 二级列表 / 主题按钮 / 选中态 / 状态栏 / `KeepSlots` / `PersistSelection` 全不执行。

**连带表现**（同一根因的次生现象，容易误导排查）：
- `SelectRegion 错误 下标越界 index=2 max=1`、`SelectTheme 错误 下标越界 index=2 max=1`
  —— Hub 只有 1 个二级、1 个主题，多余槽位本该被 `KeepSlots` 折叠，但 `KeepSlots` 因 Refresh 中断没执行，
  按钮仍可点 → 点了必然越界。
- `ApplyToHostUI 入口 uiKey=`（空）→ `分支 装扮层或UiKey为空，跳过真实界面应用`，`hasHost=false`。

### 修复（3 处，`AuctionDressUIService.lua` 69112B/1180 → 70709B/1196 行）

| # | 位置 | 改动 |
|---|---|---|
| 1 | 顶部前向声明区 | 补 `local ResolveNamedWidget = nil`；309 行 `local function ResolveNamedWidget` → `function ResolveNamedWidget` |
| 2 | `ApplyToHostUI`（806 行） | `uiKey == ""` 时按 `GetSelectedFolder(widget)` 回退取 `folderItem.Key` 并回写 `widget.DressUiKey` |
| 3 | `Refresh` | 把 `pcall(ApplyStyleThemeToFolder, …)` 从「主题列表之前」移到「主题列表 + `KeepSlots("Material")` 之后、状态栏之前」 |

第 3 点是**第二次**因预览抛错导致整层空白（第一次是 §1 的 `ApplyPreviewMaterial` 残留调用点）。
定论：**预览只是示意图，必须排在列表渲染之后并单独 `pcall`**，它失败绝不能连累列表/选中态/状态栏。
