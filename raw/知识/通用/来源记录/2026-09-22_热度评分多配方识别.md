## 1. 输入（用户反馈原文）

> 热度与评分识别不准确

用户未附截图。因此本轮先自行取证：从**真机当前画面**取一帧 2400×1080，与工具内已有的 1920×864 基准图一起，逐卡逐配方核对。

## 2. 结论速览

| 字段 | 修复前（真机 2400×1080） | 修复后 |
|---|---|---|
| 热度 | **4/6**（`116万` 读成 `16万` —— 值差 10 倍；`101万` 读成 `0万`） | **6/6** |
| 评分 | 值 6/6，但 2 张卡的原始文本被星标污染（`co4.5`、`74.3`） | **6/6**，且展示文本干净（`4.5`、`4.3`） |

| 字段 | 修复前（基准图 1920×864） | 修复后 |
|---|---|---|
| 热度 | 5/6（`111万` 只读出 `万`） | **6/6** |
| 评分 | 3/6（另有 1 个越界 `75`、2 个读空） | **4/6 + 2 个诚实留空**（那两张卡肉眼也难辨，留空不写假值） |

三类**实测**失败形态（这是本轮最有价值的部分）：

1. **前导数字丢失** —— `116万` → `16万` / `1万`；`101万` → `0万`。**静默错值，最危险**：数值列会写进一个差 10 倍甚至为 0 的数。
2. **尾部粘连** —— `73.3万` → `73.3万福`、`21.1万` → `21.1万2`；读进来的是封面上的杂字，直接进文本列。
3. **亮条淡字整块丢** —— 基准图的 `111万` 原样读只剩 `万`。

## 3. 取证方法与数据

### 3.1 「窄框 OCR」与「信息带 token OCR」的差距（决定性证据）

对同一个字段，用两种读法各读一遍（热度的例子，同一批 12 张卡）：

| 读法 | 热度命中 | 形态 |
|---|---|---|
| 工具当时的窄框读法（视图 `5.6..57.3` × `-2.2..21.7`） | 真机 4/6、基准图 5/6 | 会丢前导数字、会带尾部杂字 |
| 卡片顶部**信息带**（视图 `0..270` × `-7..32.5`）token 级 | 真机 6/6、基准图 6/6 | token 的 x 区间还能用来判断「哪块是真值」 |

信息带读法把「火苗图标 + 热度文本 + 星标 + 评分数字」一起交给 OCR，反而更稳 —— 上下文越大，检测框越不容易把首字符切掉。

### 3.2 顶部信息带是**流式排版**（颜色连通块逐列量化）

对每张卡的信息带按列统计「橙色像素」（星标与评分字都是橙/珊瑚色），把「宽 ≥10 视图单位的实心块」判为星标：

| 卡 | 星标起点（视图） | 评分数字起点（视图） |
|---|---|---|
| 基准图 r2c3 | 54.5 | 71.9 |
| 基准图 r1c2 / r1c1 | 65.7 / 64.6 | 82.0 / 82.0 |
| 真机 r1c1 / r1c2 | 59.3 / 59.3 | 76.4 / 75.9 |
| 真机 r2c3 | 62.0 | 78.6 |

即：**星标与数字的 x 随「火苗+热度文本」的宽度浮动**（热度 `111万` 比 `73.3万` 短，后面的星标就整体左移）。固定的「评分框左边界 71」因此在部分卡上会切进星标右尾 → 文本污染（`74.3` / `co4.5`）或读空。

### 3.3 被否决的方案（写下来避免后人重踩）

- **跟着星标右缘自适应**（把评分框左边界设成「星标实心块右缘 + 1」）：星标与数字**紧贴无间隙**，右缘算不准，实测把数字首位切掉 —— `3.6` → `36`、`4.3` → `3`，比固定框更差。
- **把热度框加宽到 `0..62`**：火苗被读成前导数字 —— `13.1万` → `0113.1万`、`202万` → `2202万`。**左边界只能右移，绝不能左扩。**
- **二值颜色掩膜**（红/橙像素 → 白字黑底）：会把细笔画与小数点一起吃掉 —— `4.3` → `43`、`73.3万` → `733万`，制造新的假值。改用**灰度颜色增强** `color_gray`（`clip((R−B)×2.2)`）保留中间灰度。

## 4. 修复（两层）

### 4.1 热度：多配方投票 + 假值过滤

四个配方 = {原样, 颜色增强灰} × {原框, 跳火苗框}，每个配方在 4 档放大尺度（3/4/6/8）各读一次，取该配方的众数，再按规则定值：

1. 只有一个有效值 → 采纳；
2. 多个 → **数字位数最多**的（OCR 丢字远比凭空多字常见：前导丢失已实测两次）；位数打平 → 票数多者；再打平 → **弃权**；
3. 全无效 → `sharp` + 跳火苗框复核（要求 ≥3/4 档一致）；
4. 仍无 → 留空（**错值比空值更糟**）。

`heat_value()` 另做一层假值过滤：**无单位，或数字部分以 `0` 开头**（`0万`、`0113.1万`）一律判无效。

### 4.2 评分：主读 + 多左边界兜底

主读仍是原来的「原框 + `sharp` 阶梯投票」；失败时用 `read_score_retry()` 换左边界再试（74/78 视图 × `sharp`/颜色灰 × 4/6/8 档，多数票 ≥2）。

**为什么兜底是安全的**：裁切失败的形态是「丢小数点」（`36`/`43`/`4`），`parse_score` 直接返回 `None` —— 这个兜底**只会补值、几乎不会造假值**（基准图 r1c2 由 `75`（无小数点）→ 兜底 `4.5`）。

### 4.3 展示列只放「解析命中的真值串」

`74.3`→`4.3`、`co4.5`→`4.5`、`73.3万福`→`73.3万`；原始 OCR 串留在隐藏列 `_raw_热度` / `_raw_评分`（导出自动丢弃）。用户看到的表格/导出因此不再出现星标污染。

## 6. 本轮踩到的坑

- **多配方读法不能复用 `LOBBY["fields"]` 的字段框高度**（`-2.2..21.7`）：那是「窄框读法」的**最小可用高度**，用在多配方上会把彩字上沿切掉 —— 第一次接进生产路径时，真机 `116万` 又变回 `16万` 假值。多配方统一用**信息带高度 `-7..32.5` 视图**。
- **函数返回值签名要对齐**：`read_heat` 一开始返回 `(文本, 值, why字符串)`，调用处按 `(文本, 值, detail字典)` 用 → `AttributeError: 'str' object has no attribute 'items'`。现已统一返回 `detail` 字典（含 `why`）。
- **「只有一个有效值就采纳」是最弱的一环**：实测出现过「四个配方里只有一个给出 `0万`」的情况 —— 所以必须配 `heat_value()` 假值过滤（以 0 开头判无效），否则会把这个唯一的假值当结论。
- **别急着读结果文件**：自检脚本跑完会把结果写 `_selftest.txt` 再硬退出；进程因 Tk/onnx 线程吊住时（本轮实测 30+ 分钟不退出），结果其实早已落盘 —— 按 mtime 复核再读，别把它当成「还在跑」。

## 7. 待查证 / 未验证

- `地图名` 仍是单配方读法，本轮观察到 `一刀9999修仙` 被读成 `—刀9999修仙`（`一` → 破折号）。不在本次范围内，未改；如需修，可复用同样的多配方思路。
- 「星标+数字组随热度宽度浮动」的量化样本为同一页 12 张卡（两种分辨率）；**换页签/换排序方式后是否仍成立**未验证。
- 颜色增强灰的增益 `k=2.2` 是在本机两张标定图上选的，**换机型/换主题色**可能需要重标（当前有原样配方兜底，不会因此全面失效）。
