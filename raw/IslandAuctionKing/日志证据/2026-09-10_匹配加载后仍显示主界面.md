## 订正（2026-09-15 实证）：OnRep 不是主因，服务端未开拍才是

> 证据状态：项目实测（2026-09-15，DebugID 大厅 `dkck7pkt2b60fk` → 新 DS `dkck7pkt2b60fl`）
> 本订正不删除上文，保留双方来源与适用范围。

**上文「疑似根因」把现象归因于 `OnRep_AuctionPublicState` 未触发导致大厅不关。2026-09-15 复现同类现象后逐层追日志，
结论是：服务端根本没有开拍，UI 停留在主界面只是结果。**

证据（`DSlog/TagLog/2026.09.15-16.56.50_ds__dkck7pkt2b60fl_taglog.log`）：

```
【AuctionRematchService+GetCurrentModeID】出口 modeID=1002
【AuctionRematchService+IsCurrentAuctionSubMode】出口 inAuction=true reason=AuctionSubMode
【AuctionGameService+CanStartWithCurrentHouse】分支 金币不足 PlayerKey=10001 Gold=0 MinimumGold=5000
【AuctionGameService+TryStartAfterSelections】出口 success=false error=HouseRequirementBlocked
```

客户端侧（`Clientlog/TagLog/2026.09.15-16.52.16_client__dkck7pkt2b60fk_1_TagLog.log`）：
`【AuctionHubUIService+ApplyCountdown】关键数据 display=等待开局 phase=Waiting` 恒成立。

**阻塞链**：大厅 `BuyPropGroup` 允许把金币花到 0（16:55:49 至尊仪器组 20000 → 余 10000；16:56:06 超级品鉴仪器组 10000 → 余 0）
→ 二次匹配仍然成功 → 新 DS 读存档 `Gold=0` → `Gold < MinimumGold(5000)` → `TryStartAfterSelections` 永久阻塞
→ Phase 恒为 Waiting → 大厅不关、竞拍 UI 不创建。

**对上文结论的修正**：即使 `OnRep_AuctionPublicState` 正常触发，只要服务端停在 `Phase=Waiting`，
`PublishPublicState` 下发的仍是 Waiting，客户端不可能切换到竞拍界面。因此排查顺序应为
**先确认服务端 Phase 是否推进，再查客户端 UI 切换**，而不是反过来。

**排查要点（可复用）**：二次匹配后的新 DS 是**另一个 DebugID**（本次 fk→fl，上次 fk→fl 同为末位字母递增），
日志分析器按最新文件自动选会话时只会选中其中一个，必须手工对照两个会话，否则会误判为「目标函数零命中」。

**关联修复**：见 `Script/Function/AuctionHubUIService.lua` 的 `OnMatchClicked` 新增的资产门槛拦截（2026-09-15），
以及新建的 `Asset/Data/Table/Customized/Gameplay/GameplayConfigTable`。
