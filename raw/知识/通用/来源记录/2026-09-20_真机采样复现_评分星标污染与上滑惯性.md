## 3. 问题 2 取证：评分框把星标圈进来了

### 3.1 取证方法

对评分所在的横向条带做 OCR，把**每个识别 token 的文本与其 x 区间**打出来，分别在两张不同分辨率的真机图上交叉核对（探针脚本 `probe_ocr_band.py` / `probe_ocr_1920.py`，原始输出 `probe_ocr_out.txt` / `probe_ocr_1920_out.txt`，裁切取证图 `band_*.png` / `score_*.png`，均在同目录）。

### 3.2 数据

「相对卡片左上角」的真机 px：

| 图 | 星标墨迹 | 评分数字 | 旧评分框覆盖 | 新评分框覆盖 |
|---|---|---|---|---|
| 1920×864 | ≈ 91..110 | ≈ 112..170 | 112..200（侥幸避开） | 126..205 |
| 2400×1080 | **≈ 137..165** | ≈ 165..200 | **140..250（含星标右半 140..165）** | 约 158..280（仅剩 ≈7px 星标尾） |

### 3.3 为什么必然读错

星标右缘与数字左缘**之间没有空白间隙** —— 想完整覆盖数字，框就必然带进一小条星标。星标是**实心**图形，RapidOCR 会把它当字符：

- 星标右侧弧线 → 认成 `7` → `4.3` 被读成 **`74.3`**
- 整个星标 → 认成 `?` → `2.9` 被读成 **`?2.9`**

这解释了**误读字符恒在真值左侧**（`7`、`?` 都长在真值左边），是判定「星标污染」而非「数字本身识别错」的关键形态特征。

### 3.4 同时证伪的一个旧结论

2026-09-18 曾记录「**评分框左边界固定 112**，宁可少读左边一点点，也不能让它和星标连成一块」。方向对，但**数值是拿 1920×864 单张图定的**，按比例换算到 2400×1080 后正好踩中星标。→ **旧结论作废**，现左边界为 **126@1920（视图 71.0）**，几何版本升 v4 自动清掉旧存档。

## 4. 问题 2 修复（两道防线）

1. **框**：`LOBBY["fields"]["评分"]` 从 `(62.9, -4.3, 112.3, 26.0)` 改为 `(71.0, -5.0, 115.0, 26.0)`（真机 `(112,-8,200,48)` → `(126,-9,205,48)`@1920）。
2. **解析**：新增 `parse_score()` 与 `FIELD_PARSERS = {"评分": parse_score}`，`parse_field_value()` 按字段分发。

```python
# 评分形态：「一位整数 . 一位小数」。findall 会给出全部匹配，取最后一个（真值在星标右侧）。
SCORE_RE = re.compile(r"(\d)\.(\d)")

def parse_score(text):
    if not text:
        return None, None
    s = str(text)
    if "10.0" in s:
        return 10.0, "10.0"
    hits = SCORE_RE.findall(s)
    if not hits:
        return None, None          # 没有小数点就不猜（'36' 不再被拆成 3.6）
    a, b = hits[-1]
    hit = "%s.%s" % (a, b)
    return float(hit), hit
```

**为什么两道都要**：只调框，遇到别的 DPI / 别的文件排版仍会漏进星标；只加解析器，会把「完全没小数点」的脏读也照收（且会诱使在解析层放宽，反而更危险）。**框负责不让它进来，解析器负责万一进来也读对。**

## 5. 问题 1 取证与修复：惯性，不是步长算错

大厅列表是**连续滚动**（页面底部常露出半个第三行），**一屏不是一个固定单位**。原默认：

```
shell input swipe 1200 842 1200 248 350     # 594px / 350ms
```

在 Android 手势语义里，短时长 + 大位移 = **fling（甩动）**，抬手后列表按惯性继续滚，实际位移远大于手指位移 → 一次跨过一页多。

改为：

```
shell input swipe 1200 842 1200 464 800     # 378px / 800ms
```

位移更小、按压更久 → 手势从「甩动」变「拖动」，惯性项大幅衰减。**经验判据：位移小 + 时长长 = 拖动（惯性小）；位移大 + 时长短 = 甩动（惯性大）。**

参数构造抽成纯函数，便于断言：

```python
SWIPE_PCT_DEFAULT = 0.35   # 上滑距离为屏幕高度的百分比
SWIPE_MS_DEFAULT = 800     # 按下到抬起的时长(ms)：越长惯性越小

def swipe_args(w, h, percent=SWIPE_PCT_DEFAULT, duration=SWIPE_MS_DEFAULT, display=None):
    x = int(w * 0.5)
    y1 = int(h * 0.78)
    y2 = int(h * (0.78 - percent))
    args = ["shell", "input"]
    if display is not None:
        args += ["-d", str(display)]
    args += ["swipe", str(x), str(y1), str(x), str(y2), str(duration)]
    return args
```

界面新增「上滑幅度(屏高比) / 时长(ms)」两个 Spinbox（存进 `sampler_config.json`），旁边写明「滑过头就调小幅度、拉长时长」。**不同机型 / 不同列表的滚动阻尼不一样，不存在通用值，只能给保守默认 + 现场微调。**

## 7. 本轮踩到的坑

- **给 adb 参数数组写断言不要写死下标**。H 段第一版写 `old_args[2+5] - old_args[2+3]`，实际算的是 `duration - x`（不是 y1−y2）；`new_args[2:4] == ["shell","input"]` 也取错位置（`args[2:4]` 是 `["swipe", x]`）。加了 `display` 参数后下标还会整体位移。**已改为按 `"swipe"` 关键字定位取 `(x, y1, y2, duration)`。**
- **PowerShell 回显会丢**：`& python ...` 的 stdout 经常拿不到，且不报错。改成让脚本自己写文件、再读文件；不要用 `*>` 重定向到脚本自己要写的那个文件（PS 5.1 会独占句柄，脚本侧写文件直接 `PermissionError`），且 `*>` 输出是 UTF-16，需转码后才能读。
- **自检跑一次约 1 分钟**（含 OCR 引擎初始化），跑完立刻读文件会读到上一次的旧内容 —— 按 mtime 复核再读。

## 9. 后续（同日）：「测试滑动」升级为量化测量

用户接着反馈：「**测试滑动不会实际滑动，不方便测试滑动幅度**」。

**定位**（两件事叠在一起，不是「按钮坏了」）：

1. 旧版 `test_swipe` 只判 `input swipe` 的**退出码**，成功就打一句「滑动自检通过：设备允许输入注入」。它**确实发出了滑动**，但日志里没有「滑了多少」的信息 → 用户看到「通过」却无法据此调幅度；
2. 该机（Redmi K60 至尊版 / HyperOS）`input swipe` 被 `INJECT_EVENTS` 拒绝时，按钮直接失败、根本不滑 → 这条标定路径完全不可用。

**改法：把「能不能滑」升级成「滑了多少」。**

- `measure_scroll(前帧, 后帧)`：多块模板匹配 + 中位数投票，估计内容上移的原图像素；**最佳匹配不显著优于次优（阈值 0.80）时返回 `None`**。模板取自第一帧偏下位置（`f=0.30/0.45/0.60/0.75/0.86`）—— 内容上移 s 后第一帧 y 处落到第二帧 y−s，y 越靠下能覆盖的位移上限越大。
- `swipe_advice(手指位移, 实际滚动, 页高, 幅度)`：按「实际滚动 / 一页高度」判 `没滑够(<0.7)` / `合适(0.7~1.3)` / `滑过头(>1.3)`，按比例反推建议幅度（clamp 到 0.10~0.80）。
- 「测试滑动」改名「**测一次滑动（量位移）**」：截前帧 → 滑 → **等 1.0s 惯性停下** → 截后帧 → 量位移 → 报判定 + 建议幅度。
- 新增「**测手动滑动**」：不用输入注入，等 5s 让用户手滑一次，比对两帧量出人手翻一页的实际滚动；ROM 被拦时也能标定。
- 一页 = 2 行卡片，`row_px = INT_ROW_STEP × 屏高 / 864`，`page_px = 2 × row_px`。

**验证**：自检新增 **I 段** —— 两类合成图（噪声纹理＝非周期；卡片列表＝周期排版但每行封面色与地图名不同）各 5 档已知位移（0/40/120/300/520px）**全部精确命中**（误差 ≤4px），证明周期错位不会被误判成真值；无关两帧返回 `None`；`swipe_advice` 五分支判定与建议幅度方向正确。自检 A/A2/B/C/D/E/F/G/H/**I** 全通过；回归仍 **26/30**。

> 自检 I 段第一版自己也错了：`_shifted()` 用 `crop` 后尺寸变小，两帧尺寸不一致直接判 `None`。修完又暴露一个真实缺陷 —— 模板 y 起点原本在 0.20~0.62H，**大位移（如 520px）时 `y−s` 落到负值，可比对块不足 4 个**，同样量不出。把模板下移到 0.86H 后解决。

**仍待验证**：`measure_scroll()` 只在合成图上验证过，**没有真机两帧实测**（该机注入被拦，自动滑动测不了；手动测量也需要人配合）。真机上的封面图、动效、加载占位会让匹配残差变大，是否还能稳定命中待实跑确认。

## 10. 后续（同日）：结果无法导出为表格

用户反馈：「**结果无法导出为表格**」。

**取证**：`out\` 目录 **0 个文件**（从来没成功导出过）；`.venv` 里 `openpyxl / xlsxwriter / pandas` **一个都没有**（`has=[]`）。

**定位（三处叠加）**：

1. **用户要的「表格」是 Excel 工作簿，工具只有 CSV/JSON** —— 且 venv 里没有任何能写 xlsx 的库，就算想加也没有依赖。
2. **导出异常不可见**：按钮回调里抛出的异常只打到 stderr，GUI 程序没有控制台 → 用户看到的就是「点了没反应」。最典型的触发场景是**目标 CSV 正被 Excel/WPS 打开**时再次导出 → `PermissionError`。
3. **文件落在 `out\` 但用户不知道路径** —— 弹窗只给了一次路径，事后找不到。

**改动**：

| 项 | 内容 |
|---|---|
| `write_xlsx()` | openpyxl 写工作簿：表头加粗、冻结首行、列宽自适应；`热度_值/评分_值/评论数_值` 按**数字**写（可直接排序求和），其余写文本；缺值写 `None` 而不是 0 |
| 「导出 Excel(.xlsx)」按钮 | 推荐入口 |
| `_do_export(ext, writer)` 外壳 | 空表提示 / `PermissionError`→提示先关文件 / `ImportError`→给安装命令 / 其它异常→打印 `type+msg`，同时写日志与 `messagebox` |
| 纯函数分层 | `export_rows / write_csv / write_json / write_xlsx` 全部放模块级（不弹窗、不碰控件），按钮方法只拼路径 + 调用 + 提示 → 自检才能直接断言 |
| 「打开输出目录」按钮 | `os.startfile(OUT_DIR)` |
| 依赖 | `openpyxl 3.1.5` 已装进 `.venv`（清华源） |

**验证**：自检新增 **J 段**（常驻防回归）—— `export_rows` 列序固定且缺列补空、CSV 首字节必须是 BOM `EF BB BF`（否则 Excel 开中文乱码）、表头等于 `EXPORT_COLS`、XLSX 读回 4 行（含表头）且 `热度_值=770000` 是**数字**、`地图名='别扶我！我还能跳'` 中文无损。自检 A/A2/B/C/D/E/F/G/H/I/**J** 全通过。

> **本次踩到的坑**：导出列常量 `EXPORT_COLS` 一开始放在文件末尾，而类体里的 `COLS = EXPORT_COLS` 是**类加载时求值** → `NameError: name 'EXPORT_COLS' is not defined`。常量必须定义在 `class App` **之前**；写文件的函数放末尾没问题（运行时才调用）。
> 另一处：新函数第一次被误插进类体内且缩进为 0，直接导致后面的方法缩进不一致 —— 插入大块代码前先确认锚点所在的层级。
